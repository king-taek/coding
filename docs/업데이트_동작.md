# 자동 업데이트 동작 — 무엇을 바꾸고, 의존성은 어떻게 챙기나

> 자주 나온 질문 세 가지에 답한다: (1) 자동 업데이트는 어떤 식으로 업데이트하나,
> (2) `scripts/run_this_before.py` 도 바뀌면 같이 업데이트되나, (3) 새 패키지가
> 추가됐을 때 의존성은 어떻게 갱신하나.

관련 코드: `aoi_verification/app/utils/updater.py` ·
`aoi_verification/app/ui/main_window.py`(`_on_update_found`/`_on_update_applied`).

---

## 1. 언제·어떻게 업데이트되나

- **확인 시점**: 앱 시작 직후 백그라운드로 한 번(조용히), 그리고 셋업 화면의
  **[업데이트 확인]** 버튼으로 수동.
- **비교 방법**: 동봉된 `app/VERSION`(JSON: `{sha, branch, repo}`)의 커밋 SHA 를
  GitHub 의 브랜치 HEAD 와 비교한다. 다르면 '업데이트 있음' 팝업.
- **`VERSION` 이 없으면**: 앱이 초기 파일을 만든다(`updater.ensure_version_file`,
  SHA 는 빈 값 = '미상'). 비교할 대상이 없으므로 **최신을 받아 적용하도록 안내**하고,
  한 번 받으면 진짜 SHA 가 기록돼 이후부터 정상 비교로 돌아간다.
  예전에는 이 경우 시작 시 자동 확인이 통째로 꺼져 있어서, git 아닌 소스로 만든
  포터블 빌드는 업데이트가 있다는 사실 자체를 몰랐다.
  단 **개발(git 작업트리) 실행에는 만들지 않는다** — 어차피 자동 적용이 차단된다.
- **받는 것**: 동의하면 브랜치 zip 을 받아 **앱 구동에 필요한 것을 전부** 담은 **새 트리를
  통째로 만든다**(새 모듈·리소스·문서·스크립트까지 — 누락 없음). 진행은 로딩바에 단계별
  (다운로드 → 압축 해제 → 준비 → 적용)로 표시된다.
- **검증 후에만 적용한다**: 새 트리에 `main.py`·`main_window.py`·`style.qss`·`양식.xlsx`·
  `VERSION` 등 필수 항목이 다 있는지 확인하고, 하나라도 없으면 **적용하지 않는다**(사유를
  사용자에게 표시). 예전에는 '예외가 안 났으면 성공' 이라 반쪽 트리도 적용됐다.
- **적용 시점** — 배포 형태에 따라 다르다:
  - **exe 배포**: 실행 중인 앱은 자기가 돌아가는 `app\` 폴더를 안전하게 바꿀 수 없다. 그래서
    새 버전을 `app.new\` 에 **받아두기만** 하고, **다음 실행 때 런처 exe 가 교체**한다
    (`app`→`app.old`, `app.new`→`app`). 교체 도중 중단돼도 런처가 복구한다.
  - **포터블/온라인**: 교체해 줄 런처가 없으므로 제자리에 항목 단위로 적용한다(중간 실패 시
    **전부 되돌린다**).
- **실패하면 구버전이 그대로 남는다.** `VERSION` 도 옛 것 그대로라 다음 실행에 다시 시도한다
  (예전에는 트리가 섞인 채 `VERSION` 만 안 바뀌어 같은 실패를 영원히 반복했다).
- **적용 후**: 안내 후 **프로그램을 자동 종료**한다(자동 재실행 안 함 — 사용자가 다시 실행).
- **개발/소스(git) 실행에서는 자동 적용을 하지 않는다**(`is_git_checkout` 가드).
  로컬 변경이 날아가지 않도록, 이 경우엔 `git pull` 안내만 띄운다. 즉 **자동 적용은
  포터블 빌드에서만** 일어난다.

## 2. 무엇이 바뀌고, 무엇은 안 바뀌나

| 항목 | 자동 업데이트로 바뀌나 |
|---|---|
| `aoi_verification/`(앱 코드) | **예** |
| `main.py` · `requirements.txt` | **예** |
| `docs/` · `scripts/` · 기타 구동에 필요한 파일 | **예**(전부) |
| **상류에서 삭제된 파일** | **예 — 사용자 폴더에서도 사라진다** |
| `dev/`(개발 전용 모음: `tests/`·`bench결과/`·`양식.xlsx`) | **아니오**(제외) — 단 `dev/양식.xlsx` 만 앱 루트로 따로 복사 |
| `.claude/`(저장소 작업용 스킬 모음, 198파일·4.8 MB) | **아니오**(제외) — 앱 구동과 무관한 개발 도구 |
| `결과/`(사용자 산출물) · `runtime/`(백본 IR) | **아니오** — `app\` 바깥이라 교체에 안 쓸린다 |
| `AOI_Verify.exe`(런처) · `python/`(번들 런타임) | **아니오** |
| 설치된 패키지(PyQt6·openvino …) | **아니오 — 다시 설치하지 않음** |

> 삭제 전파는 새로 생긴 동작이다. 예전에는 덮어쓰기만 해서, 저장소에서 지운 모듈이 사용자
> 디스크에 영원히 남아 계속 import 됐다(이름만 바꾼 모듈은 옛 이름이 새 코드를 가렸다).

> 제외 목록은 `updater._UPDATE_SKIP_TOP` 에서 관리한다. 구동에 필요한 새 폴더/파일은
> 별도 작업 없이 자동 포함되고, `scripts/run_this_before.py` 도 함께 받아둔다(실행은 수동).

즉 **자동 업데이트는 코드만 바꾸고 의존성 패키지는 건드리지 않는다.** 무거운 런타임을
다시 받지 않아 빠르고 안전하지만, **새 패키지가 필요한 변경은 자동으로 들어오지 않는다.**

## 3. `run_this_before.py` 는 자동 업데이트되나?

`scripts/run_this_before.py` 는 **처음 한 번** 환경을 준비하는(=`requirements.txt` 설치 +
모델 주머니 옵션 패키지 best-effort 설치) **개발용 준비 스크립트**다. 자동 업데이트는 이
파일을 최신본으로 **받아 둘 수는** 있지만(`_copy_run_this_before`), **자동으로 실행하진
않는다.** 따라서 의존성이 바뀌었다면 사용자가 한 번 갱신해 줘야 한다(아래 4).

## 4. 의존성이 바뀌었을 때 — 배포 형태마다 다르다

### exe 배포 — **설치하고, 성공해야 적용한다**

새 `requirements.txt` 가 동봉된 `python\` 런타임을 만들 때의 목록과 다르면(빌드가 남긴
`.deps_installed` 표식과 비교), **동봉된 파이썬에 직접 설치**한다. 설치가 성공해야만 코드를
적용한다 — 코드만 새것이 되면 앱이 `ImportError` 로 안 켜지고, 그게 정확히 없애려는
'반쪽 업데이트'다.

- 표식과 같으면 **아무것도 하지 않는다**(매 업데이트마다 2 GB 재설치가 돌지 않게).
- 주석·빈 줄만 바뀐 변경은 '바뀜' 으로 치지 않는다(`bootstrap.req_lines` 가 정규화).
- `--upgrade` 를 주지 않는다 — 요구사항이 전부 `>=` 라, 주면 잘 돌던 무거운 패키지까지 최신으로
  끌어올려 수 GB 를 받고 회귀 위험이 생긴다. **빠진 것만 채운다.**
- 진행은 로딩바에 busy(진행량 미상)로 표시된다. 콘솔 창은 뜨지 않는다.

설치가 실패하면(인터넷 끊김·프록시 차단 등) 업데이트를 적용하지 않고 이렇게 안내한다:

> 이번 업데이트에 필요한 패키지를 설치하지 못해 적용하지 않았습니다.
> 지금 버전은 그대로 사용하실 수 있습니다.
> 인터넷 연결을 확인한 뒤 다시 시도해 주세요. 계속 실패하면 관리자에게 새 배포본
> `AOI_Verify` 폴더 **전체(zip)** 를 요청하세요. `app` 폴더만 바꾸면 앱이 실행되지 않습니다.

> **전달하는 사람**: 그 경우 `python scripts\build.py exe` 로 다시 빌드해 `dist\AOI_Verify`
> 폴더를 통째로 zip 으로 전달한다. `app\` 만 전달하면 안 된다.

### 포터블 / 온라인 — 알림 + 수동 갱신

`requirements.txt` 의 **변경을 감지하면**(`deps_changed()`) 종료 안내에 문구를 덧붙인다:

- **개발/소스(git) 사용자**: `git pull` 후 `python scripts/run_this_before.py` 재실행.
  (이미 설치된 패키지는 'Requirement already satisfied' 로 빠르게 넘어가 여러 번 실행해도 안전)
- **포터블 사용자**: 앱 폴더의 번들 파이썬으로
  `python\python.exe -m pip install -r requirements.txt` 를 한 번 실행하거나,
  새 포터블 빌드를 받는다. (사내망은 PyPI 가 막혀 있어 보통 새 빌드를 받아야 한다.)

> 처음 도입 시점(앱 폴더에 `requirements.txt` 가 아직 없던 상태)에는 '바뀜'으로
> 오인하지 않도록, **둘 다 있고 내용이 다를 때만** 알림을 띄운다.

## 5. 백본 IR (exe 배포)

추론은 전부 OpenVINO 로 한다. torch 가 필요한 곳은 **백본을 OpenVINO IR 로 바꾸는 변환
한 번**뿐이라, 그 변환을 **빌드 시점에** 끝내고 IR 을 `runtime\ir\` 에 동봉한다
(`portable_build._build_ir` → `paths.bundled_ir_dir` → `embedder_openvino._build_ov_model`).
`app\` 바깥이라 업데이트 교체에 쓸리지 않는다.

덕분에 배포본에 torch·torchvision(그리고 그것이 끌고 오는 sympy·networkx·mpmath·
filelock·fsspec·jinja2)이 들어가지 않는다 — 번들에서 가장 큰 덩어리다. 빌드 PC 는 변환용
torch 를 임시 폴더(`.irbuild`)에 받아 쓰고 **끝나면 지운다**.

> IR 은 `.xml`(그래프)과 `.bin`(가중치)이 **짝**이다. 한쪽만 있으면 앱이 '없는 것'으로
> 보고 CPU 고전으로 폴백한다 — 반쪽짜리를 읽으면 조용히 틀린 임베딩이 나오기 때문이다.
>
> 새 백본을 추가하려면 `portable_build.IR_MODELS` 에 넣어 **빌드 때 IR 을 만들어야** 한다.
> 런타임에는 변환 수단이 없다.

## 6. 한 줄 요약

- 자동 업데이트 = **앱 코드** 교체(포터블·exe 에서만 자동). 무거운 런타임은 그대로.
- **완성·검증된 트리만 적용**되고, 실패하면 구버전과 `VERSION` 이 그대로 남아 재시도한다.
- exe 배포는 **다음 실행 때 런처가 교체**한다. 새 패키지가 필요하면 **설치하고, 성공해야**
  적용한다. 설치가 실패하면 구버전 유지 + '새 배포본 전체를 받으라' 안내.
