## 2. 이번 조사에서 새로 나온 것 — KLA 헤더가 기하를 전부 갖고 있다

앱이 아직 안 읽는 `SampleCenterLocation` 을 쓰면 KLA 파일 **하나만으로** die 격자 원점이
계산된다. 실물 3장(`dev/좌표 확인/KLA/예시1~3`)에서 검증했다.

**(1) KLA 절대좌표는 자기 헤더로 자기검산된다 — 3/3 오차 0**

```
X = XINDEX·DiePitchX + XREL − SampleCenterLocation_X
Y = YINDEX·DiePitchY + YREL − SampleCenterLocation_Y
```

**(2) `SampleTestPlan` 의 인덱스 범위 = '웨이퍼에 온전히 들어오는 die' 집합**

`SampleCenterLocation` · `SampleSize` · `DiePitch` 로 계산한 예측이 3웨이퍼 × 2축
**전부 정확히** 맞는다(`XINDEX −3..3`, `YINDEX −3..2`).

```
첫 완전열 = ceil((center − D/2)/pitch)        마지막 완전행 = floor((center + D/2)/pitch) − 1
```

**(3) 확인된 실측 쌍 1건으로 Camtek stage 기준 웨이퍼 중심이 역산된다**

`test_coords.py` 가 못 박아 둔 쌍(Camtek 예시1 ↔ KLA 예시1, die 내부 거리 119 µm):

| | 값 |
|---|---|
| Camtek | `X=272647.8  Y=165675.9` → `x_index=7  y_index=3` |
| KLA | `X=67855.3  Y=14093.7  XINDEX=2  YINDEX=0` |
| 역산 중심 | **`Center_X ≈ 204792`**, **`Center_Y ≈ 179770`** (상수로 재계산한 검산값 204700 / 179844 와 90 µm 이내) |

**(4) 그 중심으로 '완전 die 범위' 를 예측하면 — `col` 은 맞고 `row` 만 1 어긋난다**

| 축 | 기하 예측 | 실측 INI 범위 | 앱의 현재 값 | 판정 |
|---|---|---|---|---|
| X | `x_index 2..8` | `Col 2..8` | `col_origin = 2` | **일치** ✓ |
| Y | `y_index 1..6` | `Row 1..6` | `row_total = 7` | **어긋남** — 기하는 6 을 가리킨다 |

즉 `col` 은 **장비 화면 판독**과 **KLA 헤더 기하**라는 서로 독립적인 두 경로가 같은 답을 준다.
`row` 만 두 경로가 갈린다.

## 3. 유일한 미해결 — `row_total` (그리고 `KLA_ZERO_Y`)

### 두 가설

| | `row_total` | `KLA_ZERO_Y` | 근거 | 결과 |
|---|---|---|---|---|
| **A (현행)** | `ceil(D/pitch_y)` = **7** | **4** (상수) | 장비 화면 판독 1건 | 맵 행 번호 `1..6` (행 0 은 미사용) |
| **B (기하 유도)** | `floor((Center_Y + D/2)/pitch_y) − 1` = **6** | **3** (`−min(YINDEX)` 자동) | §2 의 규칙을 row 에 그대로 적용 + RDL4 LIVE 8쌍 | 맵 행 번호 `0..5` (전부 사용) |

- **두 가설은 `row_total − zero_y = 3` 으로 같다.** 그래서 KLA↔Camtek 정렬도, 매칭도 어느 쪽이든 동일하다.
- 가설 B 가 맞으면 좌표 쪽 **상수가 하나도 안 남는다**(전부 폴더에서 유도). 가설 A 가 맞으면
  `row_total`·`KLA_ZERO_Y` 는 자재가 바뀔 때마다 다시 틀릴 수 있는 값으로 남는다.

### 왜 지금 판단할 수 없나 — 장비 판독 1건 자체가 ±1 모호하다

그 판독은 **`INI Col=8, Row=5` → 화면 `col=6, row=2`** 로만 기록돼 있다(커밋 `4061b40`).
그런데 그 뒤 §6-F 에서 **INI `Row` 필드는 레시피마다 원점이 1 다를 수 있다**는 것이 밝혀졌고,
앱은 이제 그 필드를 안 쓰고 `y_index = floor(Y/pitch_y)` 를 쓴다.

```
그 결함의 레시피가 Δrow=0 이었다면  y_index = 5  →  row_total = 7   (가설 A)
                  Δrow=−1 이었다면  y_index = 4  →  row_total = 6   (가설 B)
```

**그 결함의 `X`/`Y` 를 모르기 때문에 어느 쪽인지 알 수 없다.**
(테스트에 들어 있는 `X=334789.57 Y=267755.64` 는 `Col=8/Row=5` 에 맞춰 **구성한 값**이지
판독된 실물 값이 아니다 — 커밋 메시지에는 `Col`/`Row` 만 있다.)

### 숫자로 본 갈림

| | Center_Y | 가설 B 의 `row_total` |
|---|---|---|
| TB500 예시1 (역산값) | ≈ 179,770 | **6** — 가설 A 가 되려면 `Center_Y ≥ 209,243` 이어야 한다(29 mm 위, 오차로 설명 불가) |
| RDL4 (LIVE 8쌍이 6 을 가리킴) | **미상** | `Center_Y ∈ [164,337, 209,242)` 이면 6. `Center_X` 실측이 167,449 이므로 **비슷한 값이면 맞는다** |

### 지금 상태의 실제 영향

- **매칭: 정상.** ref/val 이 같은 규칙이라 오프셋이 상쇄된다.
- **표기: RDL4 계열에서 `row` 가 1 크게 나온다**(화면·엑셀).
- **`(col,row) ±1` 게이트 예산을 이미 쓰고 있다.** 이 예산은 장비 간 규약 차이용이라,
  다른 축이 1 더 어긋나는 자재가 오면 §6-G 처럼 매치 실패가 다시 터진다.

## 4. 구해 오면 좋은 자료 — 우선순위

### ① 장비 화면 판독 — **이것 하나면 닫힌다** (필수)

**가장 좋은 형태: AOI Data Viewer 웨이퍼 맵 화면 캡처 1장.**
축 눈금이 함께 보이게 찍어 주세요. 세로 눈금이 `0..5` 인지 `1..6` 인지가 **그대로 답**입니다.

같이 필요한 것:

- 그 웨이퍼의 **WaferID / 로트**
- 그 웨이퍼 폴더의 `Params_WaferInfo.ini` (②와 겹칩니다)
- 화면에서 결함 1개를 짚었다면 **그 결함의 사진 파일명**
  (점표기 파일명 `176573.312577.c.…jpeg` 의 앞 두 토큰이 절대 `X.Y` 라 이것만 있어도 `y_index` 가 계산됩니다)

> ⚠ **결함의 `row` 숫자만 오면 지난번과 같은 모호함이 반복됩니다.** 반드시 **사진 파일명(또는 X/Y)** 을 같이 주세요.

**못 구할 때의 대안 (좋은 순서대로)**

| 대안 | 무엇 | 왜 이것도 답이 되나 |
|---|---|---|
| 1 | **AOI Data Viewer 의 VBA 소스** (`Module_Compare` 가 들어 있는 파일) | 정답 도구의 **변환식 자체**. 화면 판독보다 강한 근거다 — `±1` 게이트 규칙도 여기서 왔다 |
| 2 | 장비에서 **웨이퍼 맵을 엑셀/CSV 로 내보낸 파일** | die 목록에 col/row 가 들어 있어 눈금 범위가 그대로 드러난다 |
| 3 | 아무 웨이퍼든 **맵 화면 캡처 + 그 웨이퍼 폴더** | 웨이퍼가 달라도 됩니다. 눈금 범위와 `Params_WaferInfo.ini` 만 짝이면 판정됩니다 |
| 4 | **아무것도 못 구함** | **현행 유지가 맞습니다.** 매칭은 정상이고, 근거 없이 바꾸면 지난번 7↔6 회귀를 반복합니다. 원하시면 '표기 불확실' 을 앱이 알리도록 할 수는 있습니다(요청 시) |

### ② `Center_Y` — `Params_WaferInfo.ini` 통째로 (품 거의 안 듦)

앱은 지금 **`Center_X` 만 읽고 `Center_Y` 는 아예 안 읽습니다.** 가설 B 를 검증하려면 필요합니다.

- 위치: `…\ScanResults\<job>\Setup1\<Lot>\<WaferID>\Params_WaferInfo.ini`
- 필요한 블록: `[Geometry]` 전체 + `[Geometric]` 전체
  (`Diameter` · `MeasuredDiameter` · **`Center_X`** · **`Center_Y`** · `EBR` · `FlatNotchVal`)
- **가장 값진 것은 RDL4 로트**(`W7548306XYA2` / `W7548304XYG4` / `W7548303XYC2`)입니다.
  LIVE 8쌍이 이미 `row_total=6` 을 가리키고 있어서, `Center_Y` 가 **164,337 ~ 209,242** 안에
  있으면 가설 B 가 즉시 지지됩니다(`Center_X` 가 167,449 이니 비슷한 값이면 맞습니다).
- 파일 통째로 보내 주시는 게 제일 좋습니다. 경로 문자열 외에 민감한 내용은 없습니다.

**대안**: `Center_X/Y` 가 전부 `0.000000` 인 로트뿐이라면(= 정렬 정보 미기록) → ③으로 대체됩니다.
KLA 헤더의 `SampleCenterLocation` 이 같은 역할을 하기 때문입니다.

### ③ `Center_Y` 가 기록된 웨이퍼의 **KLA↔Camtek 확인 쌍** 1건 ← **지금 유일하게 남은 것**

9차(§6-J) 이후 이게 왜 필요한지가 더 뾰족해졌습니다. **KLA 쪽 `zero_y` 를 못 정합니다.**

| | Camtek `row_total` | KLA `zero_y` | 차(3이어야 정렬) |
|---|---|---|---|
| `Center_Y` 기록됨 (RDL4류) | 6 (유도) | 4 (상수) | **2** ← 이 로트에 KLA 스캔이 오면 row 가 1 어긋납니다 |
| `Center_Y` 미기록 (dev 샘플) | 7 (폴백) | 4 (상수) | 3 ✓ |

KLA `.001` 의 `SampleCenterLocation` 으로 계산하면 `zero_y=3` 이 나오고 그게 유도한
`row_total=6` 과 짝이 맞습니다. 그런데 그렇게 바꾸면 이번엔 **`Center_Y` 를 못 읽어
폴백한 Camtek 폴더**와 1 어긋나고, 실제로 확인된 KLA↔Camtek 쌍이 그 경우라 정렬이
깨집니다. 그래서 **바꾸지 않고 상수를 유지**해 뒀습니다.

`Center_Y` 가 기록된 웨이퍼의 KLA 쌍 1건이면 어느 조합이 맞는지 바로 정해집니다.

- 필요한 것: 같은 웨이퍼의 **Camtek 결함 사진 1장 + KLA 결함 사진 1장**, 그리고 두 폴더의
  `ColorImageGrabingInfo.ini` · KLA `.001`(헤더 40줄이면 충분) · `Params_WaferInfo.ini`
- **반드시 사람이 사진으로 같은 결함임을 확인한 쌍**이어야 합니다. 거리가 가깝다는 건 근거가
  못 됩니다 — 같은 die 안 200 µm 거리에 다른 결함이 실재했습니다(`규칙_배경.md`).
- 이게 있으면 `row_total − zero_y` 상수가 **실측으로 고정**됩니다. ①과 함께면 둘 다 유도식이 됩니다.

**대안**: KLA 스캔이 없으면 → 같은 웨이퍼의 **LIVE↔Camtek 확인 쌍**이라도 `col_origin` 은 검증됩니다.
`row` 는 여전히 ①이 필요합니다.
