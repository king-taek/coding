## 1. 죽은 코드 — CNN 임베딩 기능 (약 390줄)

### 무엇이 죽었나

`similarity/cnn_embed.py` 는 **리터럴로** 비활성이다:

```python
def is_available() -> bool:
    return False                     # ← 상수

def compute_embedding(src) -> Optional[np.ndarray]:
    return None                      # ← 상수
```

이걸 켜려면 학습된 `.pt` 가중치와 `learning/registry.py` 의 active 포인터가 필요한데,

- **`.pt` 를 만드는 학습 기능은 이미 제거됐다** (`learning/__init__.py` 가 명시).
- **`learning/registry.py` 를 import 하는 앱 코드가 0곳이다** (테스트만 씀).
- `config.SimilarityWeights.use_cnn` 기본값이 `False` 이고, 이를 `True` 로 바꾸는
  코드도 없다.

즉 되살릴 경로 자체가 없다.

### 연쇄 — 파이프라인 실행 경로도 함께 죽었다

이게 이번 리뷰에서 가장 중요한 발견이다:

```python
# similarity/slot_features.py:434
def _should_pipeline(self) -> bool:
    ...
    return bool(_cnn.is_available())      # ← 항상 False
```

`run()` 이 이 값으로 `_run_pipelined()` 와 `_run_sequential()` 을 고르므로,
**`_run_pipelined()`(52줄)는 프로덕션에서 단 한 번도 실행되지 않는다.**
producer/consumer 파이프라이닝 전체가 도달 불가 코드다.

주석에도 그렇게 적혀 있다 — "겹칠 GPU 작업은 CNN 임베딩뿐인데, 그 경로가 비활성이라
지금은 항상 False 다".  코드는 남겨 두고 사실만 주석으로 기록한 상태다.

### 삭제 후보 목록

| 줄 수 | 대상 | 근거 |
|---|---|---|
| 60 | `learning/registry.py` **전체** | 앱 참조 0회. `.pt` 산출 수단 없음 |
| 39 | `similarity/cnn_embed.py` **전체** | 리터럴 `False`/`None` |
| 77 | `slot_features` 의 `_run_pipelined`·`_should_pipeline`·`_prefetch_cnn_embeddings` | 도달 불가 |
| ~34 | `similarity/pipeline.py` 의 cnn 분기 + `Feature.cnn`·`cnn_model` 필드 | |
| ~15 | `config.py` 의 cnn 가중치 + `normalized()` 의 재분배 분기 | `use_cnn` 이 항상 False |
| 5 | `utils/paths.models_dir()` | registry 전용 |
| 37 | `dev/tests/test_registry.py` | 죽은 모듈의 테스트 |
| 120 | `dev/tests/test_pipeline_equivalence.py` | 도달 불가 경로만 검증 |
| **약 390** | **합계** (앱 232 + 테스트 157) | 앱 코드의 0.9% |

### 리스크: **낮음**

- **옛 점수 캐시 호환**: `Feature.load` 가 이미 `if "cnn" in data.files` 로 방어하고
  있어, 필드를 지워도 기존 `.npy` 를 그대로 읽는다.  반대로 옛 캐시에 남은 cnn 키는
  무시된다.  양방향 호환.
- **고효율 모드와 무관**: GPU 임베딩(고효율 모드)은 `learning/embedder_openvino.py`
  가 동봉 IR 로 따로 처리한다.  이번 삭제 대상과 코드가 겹치지 않는다 — 확인함.
- **`_score_pairs_parallel`(93줄)은 살아 있다** — 순차 경로도 쓴다.  삭제 대상 아님.

### 단점

- 나중에 CNN 재채점을 되살리고 싶으면 git 히스토리에서 꺼내야 한다.  다만 되살리려면
  어차피 학습 파이프라인부터 다시 만들어야 하므로, 지금 코드가 그때 쓸 만할 가능성은
  낮다.
- 커버리지 숫자가 살짝 흔들린다(`registry.py` 는 지금 100% 다 — 자기 테스트만으로).
  이건 오히려 **커버리지가 죽은 코드를 살아있는 것처럼 보이게 한** 사례다.

## 5. 추천 실행 순서

가장 값이 크고 리스크가 낮은 것부터:

1. **CNN 죽은 기능 제거** (1장, ~390줄) — 단일 커밋, 전체 테스트로 검증
2. **자잘한 죽은 것 + 문서 참조 6건** (2장, ~10줄)
3. **빠른 레인 오염 제거 + 레이어 테스트 추가** (4-1 #1, #3)
4. **조용한 예외 3곳 로그로** (4-1 #2)
5. **`review_context()` 도입** (4-1 #4)

여기까지가 "확실히 이득, 거의 무위험" 구간이다.  6번 이후(격자 통일·KLA 분리·
사전계산 드라이버 분리)는 각각 별도로 판단하는 것을 권한다.

지시해 주시면 1번부터 순서대로 진행하겠다.
