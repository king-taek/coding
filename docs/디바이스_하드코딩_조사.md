# 디바이스 하드코딩 조사 — TB500 기준값이 박혀 있던 곳과 대체 소스

> 배경: 평소와 다른 device 로 검증을 돌렸더니 **좌표가 완전히 엉망**으로 나왔다.
> 원인을 추적해 "TB500 한 대의 실측값이 상수로 박혀 있던 곳"을 전수 조사하고,
> 그 값들을 **스캔 결과 폴더의 파일에서 읽도록** 바꾼 기록이다.
>
> 결론부터: **필요한 값은 이미 결과 폴더 안에 다 있었다. 코드가 안 읽고 있었을 뿐이다.**

## 1. 무엇이 하드코딩돼 있었나

`aoi_verification/app/coords/models.py` 에 die 격자 상수 6개가 있었고, 좌표 변환 전체가
이 값에 의존했다. die 크기가 다른 디바이스에서는 `x = X − Col × 37247.7` 이 통째로
틀린 값을 낸다 — 이것이 "좌표가 엉망" 의 직접 원인이다.

| 상수 | 값 | 쓰이는 곳 | 대체 소스 | 상태 |
|---|---|---|---|---|
| `CAMTEK_PITCH_X` | 37247.7 µm | `camtek_ini.py` `x = X − Col×pitch` | `Params_WaferInfo.ini` `[Geometry] DieStep_X` | ✅ 전환 완료 |
| `CAMTEK_PITCH_Y` | 44905.4 µm | `camtek_ini.py` `y = Y − Row×pitch` | `[Geometry] DieStep_Y` | ✅ 전환 완료 |
| `KLA_ZERO_X` | 3 | `kla_info.py` `col = XINDEX + 3` | `.001` `SampleTestPlan` 의 `min(XINDEX)` | ✅ 전환 완료 |
| `KLA_ZERO_Y` | **4** | `kla_info.py` `row = YINDEX + 4` | ⚠ `SampleTestPlan` 최솟값으로는 불가 — §1-B. **단 `SampleCenterLocation` 기하로는 산출된다(→ §6-I, 값 3)** | 상수 유지(§6-I 미결) |
| `CAMTEK_COL_OFFSET` | 2 | `camtek_ini.py` `col = Col − 2` | 3개 device 실측에서 불변 — 고정 시스템 오프셋(§6) | 상수 유지 |
| ~~`CAMTEK_ROW_TOTAL`~~ | ~~7~~ | `row = ceil(Diameter/pitch_y) − Row` | **`[Geometric] Diameter` 로 유도** — §6 (3차 조사) | ✅ 상수 삭제 |

> `DieSize_Y`(44904.9858) 가 아니라 **`DieStep_Y`(44905.4)** 가 맞다 — 옛 상수와 정확히 일치한다.
> ⚠ `DieSize` 는 폴백으로도 쓰지 않는다 — **크기는 간격이 아니다**(§5-B).
> `KLA_ZERO_Y` 는 **2차 조사에서 교정된 값**이다(§1-B).  `CAMTEK_ROW_TOTAL` 은 2차에서
> 7 로 교정했다가 **3차(§6)에서 상수 자체를 없애고 `ceil(Diameter/pitch_y)` 유도로 대체**했다.

### 1-B. row 변환이 전 구간 1 어긋나 있었다 — 2차 조사에서 교정

장비(AOI Data Viewer) 웨이퍼 맵 직접 판독:

```
INI  Col=8, Row=5     →     장비 화면  col=6, row=2
맵 규약: 왼쪽 맨 아래가 (0,0), 오른쪽·위로 1씩 증가 (col·row 둘 다 0-based)
```

`row = a·Row + b`, `a = ±1` 로 두고 이 1건을 대입하면 답이 하나로 나온다:

| a | b | 식 | Row 1..6 → row | 판정 |
|---|---|---|---|---|
| +1 | −3 | `Row − 3` | −2 .. 3 | ✗ 음수 — 0-based 맵에 존재할 수 없다 |
| −1 | +7 | **`7 − Row`** | 1 .. 6 | ✓ |

→ `CAMTEK_ROW_TOTAL = 7`.  맵 세로 눈금은 0..6(7칸)이고 이 자재는 **1..6 만 사용**한다
(가로는 0..6 전부 사용) — "col 7개 / row 6개" 와 정확히 맞는다.

**KLA 도 함께 +1 해야 한다.** 거리 121 µm 로 동일 결함임이 확인된 쌍
Camtek `Col=7,Row=3` ↔ KLA `XINDEX=2,YINDEX=0` 에서 Camtek row 가 4 가 되므로,
KLA 도 `0 + KLA_ZERO_Y = 4` 여야 정렬이 유지된다.
**양쪽을 함께 올리므로 매칭 결과는 그대로이고 표시·엑셀의 row 숫자만 +1** 된다.

#### ⚠ 1차 구현에 대한 정정 — `SampleTestPlan` 으로는 `zero_y` 를 못 구한다

1차에서 `zero_x/zero_y` 를 `SampleTestPlan` 최솟값에서 뽑게 하고, `(3,3)` 이 나와 옛 상수와
일치하는 걸 근거로 삼았다. **그 근거는 X 에만 유효했다.**

`SampleTestPlan` 에는 **검사한 die 만** 있다. 맵 가장자리 행/열이 통째로 미사용이면 최솟값이
맵 원점과 어긋난다 — 이 자재가 정확히 그 경우다:

| 축 | 맵 눈금 | 사용 범위 | `−min(INDEX)` | 정답 | 자동 산출 |
|---|---|---|---|---|---|
| X | 0..6 | 0..6 (전부) | 3 | 3 | ✅ 가능 |
| Y | 0..6 | 1..6 | 3 | **4** | ❌ 불가 → 상수 |

> ⚠ **8차 조사에서 이 표의 '맵 눈금' 칸이 관측이 아니라 가정임이 드러났다**(§6-I).
> `SampleCenterLocation` 기하로 계산하면 이 자재의 **완전 행은 애초에 6개**(`YINDEX −3..2`)라,
> 'Y 맵이 0..6 인데 1..6 만 검사했다' 가 아니라 '완전 행이 −3..2 뿐이고 전부 검사했다' 일 수
> 있다. 그러면 `zero_y=3`·`row_total=6` 이 맞는다. 아래 장비 판독 1건이 유일한 반증인데
> 그 판독도 ±1 모호하다 — §6-I 참조.

> 이전 세션이 `CAMTEK_ROW_TOTAL` 을 7→6 으로 바꿔 이 어긋남이 생겼다. 그때 맞춘 대상은
> '현물 웨이퍼 맵' 이 아니라 **KLA 변환값** 이었고(Camtek 만 움직여 KLA 에 맞춤),
> KLA 쪽 원점이 틀렸다는 걸 못 봤다. 재발 방지용으로 장비 판독값을 테스트에 못 박아 뒀다
> (`test_coords.py::TestCamtekIni::test_equipment_screen_reading`).

### 그 밖의 device 관련 상수

| 위치 | 값 | 판단 |

## 2. 실측으로 확인한 불변식 — pitch 검산의 근거

`dev/좌표 확인/Camtek/예시1~3` 의 `ColorImageGrabingInfo.ini` **전 항목 63건**에서:

```
Col == floor(X / DieStep_X)      63 / 63 일치
Row == floor(Y / DieStep_Y)      63 / 63 일치
```

→ **Camtek 의 die 격자는 stage 원점 (0,0) 에 고정**돼 있고, `Params_WaferInfo.ini` 의
`DieStep` 이 바로 그 격자 간격이다.

이 관계는 그대로 **자체 검산**에 쓴다. 파일에서 pitch 를 읽은 뒤 같은 폴더 INI 의 Col/Row 로
위 식을 검사해서, 안 맞으면 그 값을 **채택하지 않고** 폴백 + 경고를 남긴다. 엉뚱한 키를
읽었거나 다른 웨이퍼의 INI 가 섞였을 때 조용히 틀린 좌표를 내지 않게 하는 장치다.

## 3. "KLA 에도 이런 정보가 있나요?" → **있습니다. 오히려 더 많습니다.**

`dev/좌표 확인/KLA/예시1/*.001` (KLARF 형식) 헤더 실물:

```
SampleSize 1 300;                                    ← 300 mm 웨이퍼
DeviceID "4DT-TB500-H-M1";                           ← device 이름이 데이터에 그대로 있다
StepID "RDL2_NEW(MULTI)";
SampleOrientationMarkType NOTCH;
OrientationMarkLocation DOWN;                        ← notch 방향(축 뒤집기 근거)
DiePitch 3.7247930000e+004 4.4905340000e+004;        ← die pitch X, Y (µm)
DieOrigin 0.0000000000e+000 0.0000000000e+000;
WaferID "W6459076XYG1";                              ← slot 명 (이미 읽고 있음)
Slot 10;
SampleCenterLocation 1.8460000000e+004 -2.2294100000e+002;
SampleTestPlan 30
  -3 -1   -3 0   -2 -2  …  3 -1   3 0 ;              ← 검사한 die 인덱스 전체 목록
```

`SampleTestPlan` 이 곧 `KLA_ZERO_X=3` 의 근거였던 "package X count 7 → 7//2 = 3" **그 자체**다.
실측 범위는 XINDEX −3..3(7열), YINDEX −3..2(6행).

⚠ 다만 `zero = −min(index)` 가 맞는 건 **X 뿐**이다. 이 목록에는 **검사한 die 만** 있어서
맵 가장자리 행/열이 통째로 미사용이면 최솟값이 맵 원점과 어긋난다 — 세로가 그 경우다
(산출값 3, 정답 4).  자세한 건 §1-B.

| 항목 | 전환 전 | 전환 후 |
|---|---|---|
| `DiePitch` | **Y 하나만** 읽음(y 뒤집기용) | X·Y 모두 읽음 |
| `SampleTestPlan` | 안 읽음 | **die 인덱스 원점 X 산출**(Y 는 불가 — §1-B) |
| `DeviceID`/`LotID`/`StepID`/`Slot` | 안 읽음 | (여전히 안 읽음 — 필요해지면 여기서) |
| `DieOrigin`/`SampleCenterLocation` | 안 읽음 | (절대좌표 환산이 필요해지면 여기서) |
| `OrientationMarkLocation` | 안 읽음 | (축 뒤집기 방향을 데이터로 정할 때) |

## 4. Camtek `WaferInfo.ini` — 코드가 전혀 안 읽는 파일

```
[AutoCycleInfo]
InputLot=TBD-PIDS3
InputWaferID=25195007EWF6
Machine=EagleG5_109076
ActiveSlot=5
CarrierID=12612202
FillID=25195007EWF6
UseLot=TBD-PIDS3
UseWaferID=25195007EWF6        ← ★ 이게 권위 있는 값이다 (아래 경고)
```

KLA 는 `.001` 헤더의 `WaferID` 로 폴더명과 무관하게 slot 을 식별하는데(`kla_info.read_wafer_id`),
**Camtek 은 폴더명에만 의존**한다. 이 파일을 읽으면 Camtek 쪽도 같은 수준의 식별이 가능하다.

→ 이번 변경 범위와는 별개 기능이라 **기록만 하고 손대지 않았다.** 필요하면
`kla_info.read_wafer_id` 와 같은 모양으로 추가하면 된다.

### ⚠ 단, `InputWaferID` 를 쓰면 안 된다 — 실측 3건 중 2건이 틀렸다

처음엔 이 절이 `InputWaferID` 를 쓰라고 적어 뒀다. 위 샘플 하나만 보면 세 필드가 전부
같아서 구분이 안 됐기 때문이다. 실물이 더 모이자 갈렸다:

| 로트 | `InputWaferID` | `FillID` / `UseWaferID` | 실제 폴더명 |
|---|---|---|---|
| TBD-PIDS3 (EagleG5_109076) | `25195007EWF6` | `25195007EWF6` | 일치 |
| 20260511_FDV (EagleG5_108903) | **`0`** | `W7548303XYC2` | `W7548303XYC2` |
| CYX-PIDS7 TEST (EagleT_108783) | **`W7486056XYF2`** | `W7489027XYE4` | `W7489027XYE4` |

`InputWaferID` 는 **호스트/작업자가 넣는 입력값**이라 비어 있거나(`0`) **이전 웨이퍼 값이
그대로 남아 있다.** 세 번째 줄은 같은 로트의 **다른 웨이퍼** ID 다 — 그대로 믿었으면
웨이퍼를 잘못 식별한다. 세 샘플 모두 `key_WaferIdReading=False` 라 OCR 로 갱신되지도 않는다.

→ **`UseWaferID` 를 1순위, `FillID` 를 폴백으로 쓴다.** 둘은 3건 모두 서로 같았고 폴더명과도
일치했다. `InputWaferID` 는 참고값으로도 쓰지 마라.

> KLA 쪽에서 "사진 파일명 prefix 로 WaferID 를 추측하지 마라" 와 같은 교훈이다 —
> **그럴듯한 필드 하나를 샘플 1건으로 채택하지 말 것**(→ `규칙_배경.md`).

### 장비 모델이 둘이다 — 표기 규약 차이의 후보

`Machine` 필드로 확인된 모델: **`EagleG5`**(109076, 108903) 과 **`EagleT`**(108783).
§6-G 에서 `col_origin`·`row_total` 이 자재마다 1 다른 것처럼 보이는데, 그 두 자재가
공교롭게도 서로 다른 모델이다(RDL4=EagleG5, 15호기=EagleT). **표기 규약이 모델별로 다를
가능성**이 있으니, 장비 화면 판독값을 받을 때 어느 모델인지 함께 기록할 것.

## 5. ProductInfo.ini 검토 (2차) — 무엇을 쓰고 무엇을 버렸나

### 5-A. `[Geometric] Cols`/`Rows` 는 쓸 수 없다 (확정)

| device | 파일 `Cols`×`Rows` | 실제 격자 | 차이 |
|---|---|---|---|
| TB500 | 10 × 9 | 7 × 6 | 3, 3 |
| PGEE48 | 74 × 58 | 70 × 54 | 4, 4 |

차이가 device 마다 다르고, `ceil(Diameter/pitch)+1` 은 PGEE48 은 둘 다 맞지만
**TB500 Rows 는 8** 이 나와 틀린다(파일은 9). `floor`·`round` 조합도 마찬가지다.
두 예시를 동시에 설명하는 규칙이 없으므로 **채택하지 않는다**(추정 금지).

### 5-B. ⚠ die '크기' 는 pitch 가 아니다 — `DieSize` 폴백 제거

PGEE48 이 드러낸 사실: 스크라이브 street 이 있는 자재는 크기와 간격이 다르다.

| | die 크기 | die 간격(pitch) | 차 |
|---|---|---|---|
| TB500 | `DieSize_X` 37247.7453 | `DieStep_X` 37247.700 | 0.045 µm |
| PGEE48 | `XDieSize` 4147.352 | `XDieIndex` 4160.900 | **13.548 µm (0.33 %)** |

크기를 pitch 로 쓰면 col 70 에서 누적 **948 µm = die 폭의 23 %** 어긋나고, 검산이 항목의
10.8 % 에서 실패한다. 1차 구현은 그때 **TB500 값으로 폴백**해 `x = −1,652,266 µm` 를 냈다 —
사용자가 겪은 "좌표 완전 엉망" 의 재현이다. 그래서 `DieSize_*`·`DieSelectedSize_*`·
`XDieSize/YDieSize` 는 후보에서 **완전히 뺐다**.

### 5-C. pitch 후보 — 간격(step) 계열만, 우선순위대로

| 순위 | 파일 : 키 | TB500 | PGEE48 |
|---|---|---|---|
| 1 | `Params_WaferInfo.ini` : `DieStep_X/Y` | 37247.700 / 44905.400 | (미확인) |
| 2 | `ProductInfo.ini` : `XDieIndex` / `YDieIndex` | (미확인) | **4160.900 / 5294.000** |
| 3 | `ProductInfo.ini` : `CustomerDiePitch_X/Y` | 37249.0 / 44905.8 | 4160.722 / 5293.781 |
| 4 | `models.py` 상수 | 37247.7 / 44905.4 | — |

**후보를 순서대로 돌며 검산을 통과한 첫 값**을 쓴다. 상수(4순위)도 예외 없이 검산을 받으므로,
다른 자재에서 옛 값이 조용히 쓰이는 경로가 없다. **하나도 통과하지 못하면 좌표를 만들지 않는다**
— 앱이 '좌표 정보 없음' 으로 안내한다. 틀린 좌표를 내느니 안 내는 편이 낫다.

### 5-D. 검산이 보장하는 것과 못 하는 것

실측 63건으로 후보별 검산을 돌린 결과:

```
Params DieStep    63/63 통과        PGEE48 pitch(오답)   0/63 거부
Params DieSize    63/63 통과 ←      검산 허용 구간: X (36972.7, 37259.8]
CustomerDiePitch  63/63 통과        폭 287 µm — 근사값끼리는 구분 못 한다
```

- **보장**: 다른 자재의 pitch 같은 **명백한 오답은 확실히 걸러낸다**.
- **한계**: 같은 자재의 근사값끼리는 구분하지 못한다 → **후보 순서가 정확도를 정한다.**
- TB500 에서 `DieSize` 가 통과한 건 격자가 7열뿐이라서다 — 그래서 검산에 기대지 않고
  §5-B 처럼 후보에서 아예 뺐다.

### 5-E. 소형 die 의 허용 오차 — Setup 화면에서 알린다

PGEE48(die 4.16 mm)에서 기본 허용 오차 500 µm 는 **die 폭의 12 %**, `tol×3` 은 36 % 라
오매칭 위험이 크다(TB500 은 1.3 %). Setup 화면이 감지된 die 크기를 보여주고, 허용 오차가
die 폭의 2 % 를 넘으면 경고한다. **값을 대신 바꾸지는 않는다** — 기존 결과가 조용히
달라지면 안 되기 때문이다.

## 6. 사용자 도출 규칙 채택 (3차) — row 기준을 Diameter 로 유도

사용자가 4개 데이터(서로 다른 3개 device, **장비 화면 정답** 포함)로 직접 도출한 규칙:

```
x_index = floor(X / DieStep_X)          y_index = floor(Y / DieStep_Y)
die_x   = floor(X − x_index·DieStep_X)  die_y   = floor(Y − y_index·DieStep_Y)
col     = x_index − 2
row     = ceil(Diameter / DieStep_Y) − y_index
```

전수 재검증 결과(4예시 16항목 + 장비 판독 1건 + dev 샘플 63건 전부 일치) **채택했다**.

### 6-A. `row` 기준의 정체 — 상수 7 이 아니라 `ceil(Diameter/pitch_y)`

| device | pitch_y | `ceil(300000/pitch_y)` | 상수 7 이었다면 |
|---|---|---|---|
| TB500 | 44905.4 | **7** — 옛 상수와 동일(회귀 없음) | 동일 |
| dev-A | 31831.4 | **10** — 장비 정답 일치 | **row = −2 (오답)** |
| dev-B | 47835.5 | **7** | 우연히 동일 |

2차에서 장비 판독으로 7 을 확정했지만 그건 TB500 의 **결과값**이었고, 일반식은
`ceil(Diameter/pitch_y)` 였다.  `Diameter` 는 `Params_WaferInfo.ini [Geometric]` 에서 읽는다
(`ProductInfo.ini` 폴백, 둘 다 없으면 300 mm — 실측 확인상 현재 전 device 300 mm).
`CAMTEK_ROW_TOTAL` 상수는 **삭제**했다.

### 6-B. `col − 2` — 자재별 값이 아니라 고정 시스템 오프셋

pitch_x 가 전혀 다른 3개 device(25022.9 / 37247.7 / 27474.5)에서 모두 `col = x_index − 2`.
§8 에서 "자재별 상수라 자동화 불가" 로 분류했던 것을 정정한다 — **device 불변의 고정
오프셋**이라는 실측 증거가 생겼다(물리적 의미는 미확정, 보고서 §10.2).

### 6-C. `die_x/die_y` 는 버림(floor) — 반올림이 아니다

실측: 나머지 43180.809 를 장비는 **43180** 으로 표기한다(반올림이면 43181).
기존 코드는 소수부를 보존해 `.0f` 표시가 장비 화면과 최대 1 µm 어긋났다 — 버림을 채택해
**화면·엑셀 수치가 장비와 정확히 일치**한다.  매칭 거리 변화는 2 µm 미만(ref/val 동일
규칙)이라 판정(20/500 µm)에 영향이 없다.

### 6-D. 여전히 남는 것

- **KLA `zero_y=4`**: 이 규칙으로도 유도 불가(KLA 인덱스 원점 die 의 y_index 를 알 데이터가
  없다).  row 기준이 7 이 아닌 device 에서 KLA↔Camtek 교차 검증을 하게 되면 그 쌍 데이터로
  재확인 필요.
- **Diameter ≠ 300 mm 미검증**: 4개 사례 모두 300 mm (사용자 확인: 현재 전 device 300 mm).
- **`ceil` 경계**: `Diameter/pitch_y` 가 정확히 정수인 device 는 미관측.
- **LIVE 파일명 규약**(`camtek_live`): 별도 형식이라 이번 규칙과 무관 — 불변.

골든 테스트: `dev/tests/test_wafer_geometry.py::TestGoldenEquipmentExamples` 가 4개 사례를
그대로 재현해 못 박는다.

## 6-E. die pitch 를 몰라도 매칭은 된다 — 절대 wafer 좌표 폴백 (4차)

`ColorImageGrabingInfo.ini` 의 절대 `X`/`Y` 만으로 매칭은 성립한다.  die 로 쪼개는 건
**(a) 화면·엑셀의 die-내부 좌표 표기**와 **(b) KLA 교차 매칭**(KLA 는 die-relative
`XREL/YREL` 을 주므로 같은 프레임으로 맞춰야 한다)에만 필요하다.

pitch 를 확정하지 못하면 예전엔 좌표를 아예 안 만들어 **Camtek↔Camtek 매칭까지 막혔다**.
이제 절대좌표 폴백(`source="camtek_abs"`)으로 떨어진다:

| 항목 | 값 | 근거 |
|---|---|---|
| `col` | `Col − 2` | pitch 불필요 — **정확하다** |
| `row` | `−Row` (버킷 전용) | 기준 `ceil(Diameter/pitch_y)` 를 모른다 → **꾸며내지 않는다**(음수라 장비 값이 아님이 드러난다) |
| `x`/`y` | 절대 wafer 좌표 | 그 자체로 위치 식별 가능 |

**절대좌표 비교가 die-내부 비교보다 오히려 엄격하다.**  die-내부로 재면 인접 die 의 같은
상대위치 결함이 거리 0 으로 보여 오매칭했는데(±1 이웃 게이트 때문), 절대좌표로 재면 정확히
1 pitch 만큼 떨어져 있어 기각된다.

프레임이 섞여도(절대 x≈10만 vs die-내부 x≈1만) 거리가 `tol×3` 을 한참 넘어 **자동으로
기각**되므로 별도 가드가 필요 없다.

표시는 있는 사실만 적는다 — `col 2 (row 미상 — die 크기 정보 없음)` + `wafer x … / y …`.
die-내부 좌표인 척하지 않는다.

> ⚠ 이 폴백에서는 **KLA 교차 매칭이 안 된다**(프레임이 달라 거리로 기각된다).
> 그건 원래도 pitch 없이는 불가능한 일이라 잃는 게 없다.

## 6-F. INI 의 `Col`/`Row` 는 die 인덱스가 아니다 — 레시피마다 원점이 다르다 (5차)

15호기(`R_TB500_LIVE_PI2`) 스캔에서 웨이퍼 폴더 4개가 전부 `die 기하를 확정하지 못했다` 로
나왔다. `Params_WaferInfo.ini` 에 `DieStep_X/Y` 가 멀쩡히 있는데도 §2 의 검산이 거부했다.

### 결정적 증거 — 같은 결함을 두 레시피가 각각 찍은 쌍

`RecipesInfo.ini` 가 이 스캔에 레시피가 둘임을 알려준다
(`[Recipe-1] SURFACE_M`, `[Recipe-2] PI BUBBLE`). 그리고 두 폴더에 **같은 결함이
레시피별로 한 장씩** 들어 있었다:

| 폴더 | ΔX | ΔY | `Col` | INI `Row` | die_y — INI Row 사용 | die_y — 좌표에서 유도 |
|---|---|---|---|---|---|---|
| W7489335XYF2 | −0.667 µm | −0.296 µm | 4 = 4 | 3 → **4** | 29557 vs **−15349** | 29557 vs 29556 |
| W7489341XYA1 | −1.432 µm | +0.383 µm | 8 = 8 | 3 → **4** | 33599 vs **−11306** | 33599 vs 33600 |

**같은 물리 위치, 같은 `Col`, `Row` 만 정확히 1 차이난다.** 11건 전수도 깨끗이 갈린다:

```
recipe1 (SURFACE_M) : 3건   Δcol=[0]   Δrow=[0]
recipe2 (PI BUBBLE) : 8건   Δcol=[0]   Δrow=[-1]
        (Δ = floor(좌표/DieStep) − INI 필드)
```

`Col` 은 11/11 이 `floor(X/DieStep_X)` 와 일치한다 — **pitch 는 처음부터 맞았다.**
`Row` 필드만 레시피별로 원점이 다르다. die 내부 y 가 **−15349** 로 나온 게 그 증거다
(die 안의 위치가 음수일 수 없다).

TB500 샘플 63건은 recipe 1·2 모두 `Δrow=0` 이라 둘이 같은 값이었고, 그래서 안 드러났다.

### 무엇을 고쳤나

§6 의 규칙은 처음부터 `y_index = floor(Y/DieStep_Y)` 였는데 코드가 그 자리에 INI 필드를
넣고 있었다. **새 규칙을 만든 게 아니라 문서화·장비검증된 규칙대로 맞춘 것이다.**

| | 전 | 후 |
|---|---|---|
| 좌표 변환 | INI `Col`/`Row` 필드 | **`floor(좌표/pitch)` 로 유도** |
| 검산 X | `Col == floor(X/px)` | **그대로 (완화 금지)** |
| 검산 Y | `Row == floor(Y/py)` | **레시피별로 차이가 상수** (0 일 필요 없음) |

⚠ **X 등호를 같이 완화하면 안 된다.** 항목이 1건뿐인 폴더에서 '차이가 상수' 는 공허하게
참이 돼, §5-B 의 안전장치(`test_other_device_never_gets_tb500_numbers`)가 뚫린다 —
PGEE48 자재에 TB500 상수가 채택돼 `x = −1,652,266 µm` 가 다시 나온다. 실제로 기존 거부
경로는 **전부 X 축에서 걸린다**. 완화는 딱 필요한 만큼(Y 축, 레시피별)만 했다.

### 부수적으로 확정한 것

- **`RecipesInfo.ini` 는 레시피별 `DiePitchX/DiePitchY` 를 갖고 있다**
  (Recipe-1 37248.3/44905.3 = `DieStep`, Recipe-2 37247.7/44906.1).
  차이가 0.6~0.8 µm/die 라 11건 전부에서 **인덱스가 하나도 안 바뀌고**, ref/val 이 같은
  폴더 pitch 를 쓰므로 거리에서 상쇄된다. 후보를 늘리면 '어느 레시피 것을 쓸지' 라는 새
  판단이 생기므로 **pitch 후보로는 채택하지 않았다**. 필요해지면 여기서 시작할 것.
- **결함이 0 건이면 `ColorImageGrabingInfo.ini` 자체가 안 만들어진다**(사용자 확인).
  그 폴더는 `Params_WaferInfo.ini` 유무로 'Camtek 슬롯인데 결함 0건(정상)' 임을 알 수 있다.
- **웨이퍼 전경 사진**(`CognexInSight…jpg`)이 슬롯마다 1장씩 있다(사진 수 = INI 항목 + 1이
  전 폴더에서 성립). 좌표가 없어 매칭에 못 쓰므로 `is_ignored_name` 이 열거 단계에서 뺀다.

### 남은 것

- 15호기의 `row` **표시값**이 장비 화면과 맞는지는 미검증이다.
  `row = ceil(Diameter/pitch_y) − y_index` 는 §6-A 가 4개 device 장비 정답으로 확정한
  식이지만 15호기 판독값은 아직 없다. 매칭은 ref/val 이 같은 규칙이라 영향 없다.
- INI `Row` 가 recipe-2 에서 **왜** +1 인지는 미상(장비 내부 규약). 변환에 안 쓰므로
  매칭·표기에는 영향이 없다.

회귀 가드: `dev/tests/test_wafer_geometry.py::TestRecipeRowOriginDiffers` (11건 전수 +
결정적 쌍 2개 + 'X 등호는 안 뚫린다'), `::TestFrameUnification`.

## 6-G. LIVE 파일명의 row −1 정규화 — 되돌려진 변경의 잔재 (6차)

1차 리뷰를 거친 사진은 LIVE 파일명을 쓴다. 같은 웨이퍼(`W7548303XYC2`)의 같은 결함인데
LIVE 사진과 Camtek 사진이 **매치 실패**했다.

```
LIVE : TB500_RDL4 - Multi_FDV-RDL4_W7548303XYC2_3_0_27582.7103387744_43144.6146330819_Foreign Material
INI  : 176573.312577.c.597332200.1   (X=176574.76, Y=312576.83, Col=4, Row=6)
```

`DieStep` = 37247.9 × 44905.3, `Diameter` = 300000 → `row_total = 7`.

| | col | row | die (x, y) |
|---|---|---|---|
| Camtek INI | 2 | **1** | (27583, 43145) |
| LIVE 토큰 | 3 | **0** | (27582.7, 43144.6) |
| LIVE — 예전 코드 | 3 | **−1** ← `토큰 − 1` | (27582.7, 43144.6) |

**die 좌표는 0.48 µm 차이**(`CONFIDENT_DIST` 20 의 40분의 1)로 같은 점이 확실한데,
`(col,row) ±1` 게이트에서 `Δrow = −2` 라 버킷에서 탈락했다.

### 원인 — 짝을 이루던 변경만 되돌려졌다

`e90c48d`(2026-07-14)가 한 커밋에서 **둘을 짝으로** 바꿨다:

- `models.py`: `CAMTEK_ROW_TOTAL` **7 → 6**
- `camtek_live.py`: row 토큰 **`−1` 정규화** ("안 하면 INI↔LIVE 소스 간 1 어긋남")

그 뒤 **§1-B(2차)가 장비 화면 판독으로 `7 − Row` 가 맞다고 확정**해
`CAMTEK_ROW_TOTAL` 을 되돌렸고, §6(3차)에서 상수를 없애고 `ceil(Diameter/pitch_y)` 유도로
대체했다. **`camtek_live` 의 `−1` 은 같이 되돌려지지 않았다.** 그래서 그 이후로 INI 와
LIVE 는 항상 1 어긋나 있었고, `±1` 게이트가 흡수해 줘서 안 드러났다. 이번 로트는 col 이
이미 1 어긋나 있어 **합이 2가 되면서 터졌다.**

### 전제가 실물로 반증된다

`−1` 의 근거였던 "row 토큰은 Camtek 표시 규약 **1..6**" 이라는 전제가 틀렸다 —
이번 실물 파일의 row 토큰은 **`0`** 으로, 주장한 범위 밖이다.

### 교차 확인

보고서 예시 1 의 Camtek 항목이 내는 `(col,row)` 는 `(4,5)` 이고, 대응하는 LIVE 파일명의
토큰도 `(4,5)` 다 — **원래 같은 값**이다. 예전 코드는 `(4,4)` 로 만들어 어긋나게 했다.

| | Δcol | Δrow | |
|---|---|---|---|
| 보고서 예시 쌍 — 전 | 0 | −1 | 게이트가 흡수(우연히 동작) |
| 보고서 예시 쌍 — 후 | 0 | **0** | 정확 일치 |
| RDL4 실측 쌍 — 전 | +1 | **−2** | **탈락 = 매치 실패** |
| RDL4 실측 쌍 — 후 | +1 | −1 | 통과 → 거의 정확히 일치(0.48 µm) |

### 남은 오프셋 — `col_origin=2` 는 KLA 로 **독립 확인됐다**

수정 후에도 RDL4 는 `(Δcol, Δrow) = (+1, −1)` 이다. LIVE 토큰이 `col_origin=1,
row_total=6` 을 쓰는 것처럼 보여서, 한때 `ceil((Center_X − Diameter/2)/DieStep_X)` 로
유도하는 안을 검토했다. **두 근거로 기각한다.**

**(1) `Center_X` 는 항상 있는 값이 아니다.** `W6458244XYE1`(`TB500_RDL1 - Multi`)의
`Params_WaferInfo.ini` 는 `Center_X=0.000000`, `Center_Y=0.000000`, `MeasuredDiameter=0`
이다 — 기록되지 않은 웨이퍼가 실재한다. 그 식을 쓰면 `ceil(−150000/37247.9) = −4` 라는
말도 안 되는 값이 나온다.

**(2) KLA 가 `col_origin=2` 를 독립적으로 확인해 준다.** `zero_x` 는 KLA `.001` 의
`SampleTestPlan` 만으로 산출된다(`−min(XINDEX)`) — Camtek 에 맞춰 튜닝한 값이 아니다.
그 값이 Camtek `col_origin=2` 와 정확히 맞는 실측 쌍:

| Camtek 사진 | Camtek | KLA 사진 | KLA | Δ | 거리 |
|---|---|---|---|---|---|
| `278197.216679…1` (recipe1) | (5, 3) | `FrontSideADRImg_572445` | (5, 3) | 0, 0 | 125 µm |
| `278199.216685…2` (recipe2) | (5, 3) | `FrontSideADRImg_572445` | (5, 3) | 0, 0 | 125 µm |

**사용자가 사진으로 확인한 쌍**이다(20.8 × 16.9 µm 큰 결함이라 두 장비가 다 잡았다).
웨이퍼 `W6458244XYE1`, KLA 장비 `"Tool"`, 스텝 `RDL1_NEW`, Camtek `EagleG5` x20/x5 —
기존 예시1~3(장비 `"K3"`, `RDL2_NEW`)과 **독립적인 로트**다. `col_origin` 이 1 이었다면
Camtek col 이 6 이 돼 KLA 5 와 어긋난다. 어긋나지 않았다.

> ⚠ 조사 중 `328398.139058…2` ↔ `FrontSideADRImg_572458`(185 µm) 도 쌍으로 넘겨짚었는데
> **사용자 확인 결과 다른 결함이었다.** 거리가 기존 확인쌍(112~125 µm)과 같은 범위여도
> 짝이라는 증거가 못 된다 — 같은 die 안 200 µm 거리에 **다른 결함**이 실재한다.
> 쌍은 **사람이 사진으로 확인한 것만** 근거로 쓴다(→ `규칙_배경.md`).
> 앱은 이 경우를 이미 옳게 처리한다: `CONFIDENT_DIST`(20 µm)를 넘으므로 '거의 정확히
> 일치' 로 단정하지 않고 차순위 후보로 띄워 사람이 고르게 한다.

같은 결함의 **recipe1·recipe2 사진이 둘 다** 같은 KLA 결함에 붙는 것도 확인됐다.

> ⚠ 다만 **이 웨이퍼는 §6-F 의 수정 경로를 태우지 않는다.** 두 레시피 모두
> `Δcol=Δrow=0`(INI 필드 == `floor(좌표/pitch)`)이라, 유도로 바꾸든 필드를 그대로 쓰든
> 결과가 같다. 즉 이 쌍은 **`col_origin`·KLA 정렬을 확인**하지만 **레시피별 Row 원점
> 처리를 검증하지는 못한다.** 그건 15호기(`EagleT_108783`, LOT `CYX-PIDS7 TEST`)처럼
> `Δrow` 가 레시피마다 다른 웨이퍼의 KLA↔Camtek 쌍이 있어야 한다.

→ **결론: 앱의 `col_origin=2` 가 맞고, LIVE 파일명 토큰이 자체 규약(+1/−1)을 쓴다.**
`row_total=7` 은 이 쌍과 **모순되지 않지만** 독립 확인은 아니다(`zero_y=4` 가 유도값이
아니라 상수라 순환이다 — §1-B). 그건 여전히 장비 화면 판독이 필요하다.

회귀 가드: `test_coords.py::test_real_pair2_zero_x_is_derived_and_confirms_col_origin`,
`::test_real_pair2_kla_camtek_align`.

### 곁가지로 확인한 것

이 로트(RDL4)는 표본 30건에서 `recipe1`·`recipe2` 모두 `Δcol=[0]`, `Δrow=[0]` 이다 —
§6-F 의 레시피별 Row 원점 차이는 **15호기 로트 고유 현상**이고 여기엔 없다.

## 6-H. `col_origin`·`row_total` 은 상수가 아니다 — 웨이퍼의 stage 위치를 따른다 (7차)

사용자가 **사진으로 확인한 LIVE↔Camtek 쌍 8건**(RDL4 로트, 웨이퍼 W7548306XYA2 ·
W7548304XYG4 · W7548303XYC2)을 받았다. 전부 같은 결과다:

```
Δcol = +1,  Δrow = −1     8/8 일정,  die 내부 좌표는 0.2 ~ 18 µm 안에서 일치
```

§6-G 는 이 오프셋을 "LIVE 토큰의 자체 규약" 으로 보고 열어 뒀다. **그게 틀렸다.**

### 근거 1 — 앱이 음수 col 을 낸다 (내부 모순)

W7548306XYA2 의 관측 `Col`(=x_index) 범위는 1..7 이다. 앱의 `col_origin=2` 로는

```
col = 1 − 2 = −1        ← 0-based 웨이퍼 맵에 음수 열은 존재할 수 없다
```

가 나온다. 장비 화면 판독 없이도 성립하는 모순이다. LIVE 토큰 규약(`col_origin=1`,
`row_total=6`)으로 재면 `col 0..6`, `row 0..5` 로 깔끔한 0-based 범위가 된다.

### 근거 2 — 웨이퍼 위치로 유도되고, 두 자재를 모두 설명한다

`col_origin` = **완전히 웨이퍼 안에 들어오는 첫 die 열**:

```
col_origin = ceil((Center_X − Diameter/2) / DieStep_X)
```

| 자재 | `Center_X` | 왼쪽 끝 | 유도값 | LIVE·기존 근거 |
|---|---|---|---|---|
| RDL4 (XYA2·XYG4·XYC2) | 167448.97 | 17449.0 | **1** | LIVE 8쌍이 1 ✓ |
| 15호기 (XYE4) | 204586.50 | 54586.5 | **2** | 기존 상수 2 ✓ |
| RDL1 (W6458244XYE1) | **0.000000** | — | 산출 불가 | KLA 가 2 를 확인(§6-G) |

RDL1 은 `Center_X=0`, `MeasuredDiameter=0` 으로 **기록되지 않은** 웨이퍼다 — 식이 틀린
게 아니라 입력이 없는 경우다. (조사 중 이 케이스를 보고 식을 한 번 기각했었다. 판단이
틀렸다 → `규칙_배경.md`.)

`row_total` 도 같은 논리로 **마지막 완전 die 행**이며, RDL4 에서 6 이 나와 LIVE 와 맞는다.

### 지금 상태 — 매칭은 정상, **표기가 틀렸다**

8쌍을 `(col,row) ±1` 이웃 게이트에 실제로 태우면 **3/3 이 1순위로 정확 매칭**된다
(거리 2~4 µm). ref/val 이 같은 규칙을 쓰므로 오프셋이 상쇄되기 때문이다.
**틀리는 것은 화면·엑셀에 찍히는 `col`/`row` 숫자와, KLA 교차 정렬이다.**

다만 게이트의 ±1 여유를 이 오프셋이 **이미 쓰고 있다.** 그 예산은 장비 간 규약 차이용
이므로(→ `규칙_배경.md`), 다른 축이 1 더 어긋나는 자재가 오면 §6-G 처럼 또 터진다.

### 어떻게 고쳤나 — `col` 만 유도로 바꿨다

```python
col_origin = ceil((Center_X − Diameter/2) / DieStep_X)      # Center_X 가 있을 때
           = CAMTEK_COL_OFFSET (2)                          # 없거나 0(미기록)이면
```

`Center_X` 미기록(`0`)·비상식적 결과는 상수로 폴백하고 경고를 남긴다.
적용 결과(실측):

| 자재 | `col_origin` | 결과 |
|---|---|---|
| RDL4 (Center 167449) | 2 → **1** | col 이 LIVE 8쌍과 **정확히 일치**, 음수 col 사라짐 |
| 15호기 (Center 204587) | **2 그대로** | 불변 |
| RDL1 (Center 미기록) | **2 폴백** | 불변 — KLA 정렬 유지 |
| 골든 4사례 (Center 없음) | **2 폴백** | 오차 0 불변 |

**`row_total` 은 안 바꿨다.** 같은 논리로 유도하면 RDL4 는 6 이 돼 LIVE 와 맞지만,
**15호기는 유도값 6 과 현재값 7 이 갈리는데 판단할 데이터가 없다**(§1-B 의 장비 화면
판독 1건은 `Center` 를 모르는 다른 웨이퍼다). 그래서 row 는 `ceil(Diameter/pitch_y)` 를
유지한다 — RDL4 에서 row 만 1 어긋난 채 `±1` 게이트가 흡수한다.
→ **장비 화면 판독 1건이면 닫힌다.**

회귀 가드: `test_wafer_geometry.py::TestLiveTokenOffsetIsSystematic`
(LIVE 8쌍 · col 유도 · Center 미기록 폴백).

## 6-I. KLA 헤더만으로 die 격자 원점이 계산된다 — `zero_y` 는 '유도 불가' 가 아니었다 (8차)

앱이 아직 안 읽는 `SampleCenterLocation` 을 쓰면 KLA `.001` **한 장으로** 격자 원점이 나온다.
실물 3장(`dev/좌표 확인/KLA/예시1~3`)에서 확인했다.

**(1) 절대좌표가 자기 헤더로 자기검산된다** — 3/3 오차 0

```
X = XINDEX·DiePitchX + XREL − SampleCenterLocation_X       (Y 도 동일)
```

**(2) `SampleTestPlan` 의 인덱스 범위 = '웨이퍼에 온전히 들어오는 die' 집합**

`SampleCenterLocation`·`SampleSize`·`DiePitch` 로 계산한 예측이 3웨이퍼 × 2축 **전부** 맞는다
(`XINDEX −3..3`, `YINDEX −3..2`). 즉 §1-B 가 "가장자리 행이 미사용이라 최솟값이 원점과
어긋난다" 고 본 것은 **검사 여부의 문제가 아니라 애초에 완전 행이 6개**였던 것이다.

```
첫 완전열 = ceil((center − D/2)/pitch)     마지막 완전행 = floor((center + D/2)/pitch) − 1
```

**(3) 확인된 실측 쌍 1건으로 Camtek stage 기준 웨이퍼 중심이 역산된다**

`test_coords.py` 의 확인 쌍(Camtek 예시1 ↔ KLA 예시1, die 내부 119 µm)에서
`Center_X ≈ 204792`, `Center_Y ≈ 179770`. 그 중심으로 §6-I-(2) 를 돌리면:

| 축 | 기하 예측 | 실측 INI 범위 | 앱 현재 값 | 판정 |
|---|---|---|---|---|
| X | `x_index 2..8` | `Col 2..8` | `col_origin = 2` | **일치** — 장비 판독과 독립적으로 확인 |
| Y | `y_index 1..6` | `Row 1..6` | `row_total = 7` | **1 어긋남** — 기하는 6 |

### ⚠ 그래서 §1-B 의 장비 판독 1건은 **±1 모호하다**

그 판독은 `INI Col=8, Row=5 → 화면 col=6, row=2` 로만 기록돼 있는데, §6-F 이후 INI `Row`
필드는 레시피마다 원점이 1 다를 수 있음이 밝혀졌고 앱은 그 필드를 안 쓴다.
**그 결함의 `X`/`Y` 를 모르므로** `y_index` 가 5 인지 4 인지 알 수 없다 →
`row_total` 은 7 일 수도 6 일 수도 있다. (테스트의 `X=334789.57 Y=267755.64` 는
`Col=8/Row=5` 에 맞춰 **구성한 값**이고 판독된 실물 값이 아니다 — 커밋 `4061b40` 참조.)

두 가설은 `row_total − zero_y = 3` 으로 같아 **매칭·KLA 정렬은 어느 쪽이든 동일**하다.
갈리는 것은 화면·엑셀의 `row` 숫자뿐이다.

| | `row_total` | `KLA_ZERO_Y` | 남는 상수 |
|---|---|---|---|
| A (현행) | `ceil(D/pitch_y)` = 7 | 4 (상수) | 2개 |
| B (기하 유도) | `floor((Center_Y+D/2)/pitch_y) − 1` = 6 | 3 (자동 산출) | **없음** |

RDL4 의 LIVE 8쌍은 B(=6)를 가리킨다. → **§6-J 에서 실물로 확정됐다(B가 맞다).**

## 6-J. `row_total` 확정 — 같은 결함이 두 형태로 확보됐다 (9차)

사용자가 RDL4 로트 실물을 올려 줬다(`docs/RDL4 LOT files(26년 05월, FDV)/`,
17호기·18호기 × 웨이퍼 2장). §6-I 가 남긴 ±1 모호함이 여기서 **닫힌다.**

### 결정적 증거 — 같은 결함이 두 이름으로 있다

18호기 폴더에 **같은 사진**이 두 형태로 들어 있다(사진을 열어 대조 확인, 같은 결함·같은 시야).

> ⚠ 두 파일이 원래 한 폴더에 같이 있는 건 아니다 — **사용자가 1차 리뷰를 거친 사진을
> 직접 가져다 놓은 것**이다(사용자 확인). 좌표가 파일명에 박힌 형태는 실제로 드물게 쓰인다.
> 그래도 같은 웨이퍼·같은 결함의 장비 산출값이라는 사실은 그대로다(die 좌표 0.02 µm 일치).

```
51216.183928.c.1345447384.1.jpeg                     ← 절대 X/Y 는 INI 가 갖는다
TB500_RDL4 - Multi_FDV-RDL4_W7548306XYA2_0_2_13969.17941697_4306.11285221326_….jpg
                                          └col┘└row┘└─ die 내부 x ─┘└─ die 내부 y ─┘
```

die 내부 좌표가 **0.02 µm** 안에서 같다. 즉 두 번째 이름의 `col`/`row` 는 **장비가
자기 좌표로 계산해 적은 값**이다 — 별도 규약이 아니라 정답 그 자체다(§6-G 가 "LIVE
토큰의 자체 규약" 으로 열어 뒀던 가능성이 여기서 닫힌다).

| 웨이퍼 | 장비가 적은 값 | 옛 식(`ceil(D/py)`=7) | 유도식(`Center_Y`→6) |
|---|---|---|---|
| W7548306XYA2 | `col=0 row=2` | `col=0 row=3` ✗ | `col=0 row=2` ✓ |
| W7548304XYG4 | `col=5 row=4` | `col=5 row=5` ✗ | `col=5 row=4` ✓ |

사용자 신고와 정확히 일치한다 — 단일 사진 정보에 점표기 사진을 넣으면 `5,5` 가 나오는데
실제는 `5,4`. **`col` 은 이미 `Center_X` 유도라 맞았고, `row` 만 옛 식이 남아 1 컸다.**

### `Center_Y` 는 파일에 있었다 — 앱이 안 읽었을 뿐

```
[Geometric] Diameter=300000  Center_X=167448.9731  Center_Y=179674.0034  EBR=0
```

`col_origin` 규칙을 세로축에 그대로 적용하면(축 방향만 반대 — Camtek 은 Y 가 아래로 커져서
*마지막* 완전 행이 row 0):

```
col_origin = ceil((Center_X − D/2)/pitch_x)       = 1
row_total  = floor((Center_Y + D/2)/pitch_y) − 1  = 6
```

이 예측이 **4개 폴더 결함 328건의 die 인덱스 범위와 정확히 일치**한다
(`x_index 1..7`, `y_index 1..6` → `col 0..6`, `row 0..5`). 17호기·18호기가 같은 값이고,
`Center_*` 는 두 장비·두 웨이퍼가 모두 같다 — **레시피/셋업 값**이지 웨이퍼별 실측이 아니다.

### 옛 장비 판독(§1-B)과 모순되지 않는다

`INI Col=8, Row=5 → col=6, row=2` 는 새 규칙에서도 `col=6` 이 그대로 나오고, `row=2` 는
그 결함의 INI `Row` 필드가 `y_index + 1` 이었다면 성립한다 — §6-F 에서 실제로 관측된
현상이다. 그 결함의 `X`/`Y` 를 모르므로 증명은 못 하지만 **반증도 아니다.**
(사용자 확인: 장비 맵 화면에는 **축 눈금이 없다** — 그 판독을 재현할 방법이 없다.)

### 무엇을 바꿨나

- `row_total` = `Center_Y` 유도. **미기록이면 옛 식 `ceil(Diameter/pitch_y)` 로 폴백** —
  장비 화면 정답 4사례(`TestGoldenEquipmentExamples`)가 `Center_Y` 를 안 갖고 있어
  그 값이고, 그래서 안 깨진다.
  ⚠ **두 식은 보통 1 다르다.** 폴백은 '모를 때의 기존 동작 보존' 이지 같은 값이 아니다.
- **KLA `zero_y` 는 안 건드렸다.** `SampleCenterLocation` 으로 산출하면 3 이 나오고(§6-I),
  그게 유도한 `row_total` 과 짝이 맞는다. 하지만 그러면 `Center_Y` 를 못 읽어 폴백한
  Camtek 폴더와 **1 어긋난다** — 확인된 KLA↔Camtek 쌍이 정확히 그 경우라 실제로 정렬이
  깨졌다. 그리고 이건 픽스처가 부실해서가 아니다: **`Params_WaferInfo.ini` 는 결함 사진과
  같은 폴더에 늘 있고**(사용자 확인), 그럼에도 `Center_X=Center_Y=0.000000`(정렬 정보
  미기록)인 웨이퍼가 실재한다(RDL1 `W6458244XYE1`, TBD-PIDS3). 즉 폴백 경로는 **실제
  운영 경우**다. 어느 조합이 맞는지는 **`Center_Y` 가 기록된 웨이퍼의 KLA 쌍**이 있어야
  정해진다(`좌표_검증_필요자료.md` ③). 그때까지 상수를 유지한다.

| | Camtek `row_total` | KLA `zero_y` | 차(3이어야 정렬) |
|---|---|---|---|
| `Center_Y` 기록됨 (RDL4류) | 6 (유도) | 4 (상수) | **2** ← 그 로트에 KLA 가 오면 1 어긋난다 |
| `Center_Y` 미기록 (dev 샘플) | 7 (폴백) | 4 (상수) | 3 ✓ |

회귀 가드: `test_wafer_geometry.py::TestRowTotalFromCenterY`(실물 INI 값 ↔ 같은 사진의
파일명 토큰 · 미기록 폴백 · 비상식 값 거부), `::TestRdl4RealFolders`(실물 폴더 그대로 —
17·18호기, 두 사진 형태가 같은 값 · 유도 범위 == 실측 인덱스 범위).

## 6-K. `KLA_ZERO_Y` 는 상수가 아니었다 — device 마다 다르다 (10차)

사용자가 두 device 의 실물과 **장비로 확인한 대응값**을 줬다
(`docs/KLA 좌표 예시(TB500, T254)/`, `docs/Camtek 좌표 예시(T254)/`).

### KLA — `SampleCenterLocation` 으로 유도하면 7/7 맞는다

`zero = −ceil((SampleCenterLocation − D/2) / DiePitch)` (Camtek `col_origin` 과 같은 규칙):

| device / 웨이퍼 | pitch | SampleCenterLocation | 유도 `zero_x, zero_y` | 옛 상수 |
|---|---|---|---|---|
| T254 `00MEU018XYG1` | 14406.5 × 31123.4 | (7071.0, 15443.0) | **9, 4** | 9, 4 (우연히 일치) |
| TB500 `08235234EWA1` | 37247.9 × 44905.3 | (18261.0, −134.0) | **3, 3** | 3, **4** ✗ |

사용자가 장비로 확인한 KLA↔Camtek 대응 7건이 **전부** 이 값으로 재현된다:

```
08235234EWA1_2_-1_7_1   → (5,2) ✓     00MEU018XYG1_-1_4_23_1  → (8,8)  ✓
08235234EWA1_-2_-2_31_2 → (1,1) ✓     00MEU018XYG1_4_3_23_2   → (13,7) ✓
08235234EWA1_-2_0_7_3   → (1,3) ✓     00MEU018XYG1_4_-2_31_3  → (13,2) ✓
                                      00MEU018XYG1_-8_-2_23_4 → (1,2)  ✓
```

→ **`KLA_ZERO_Y=4` 상수를 쓰던 동안 TB500 자재의 KLA row 가 전 구간 1 컸다.**
이제 유도하고, 상수는 `SampleCenterLocation` 이 없을 때의 폴백으로만 남는다.
5웨이퍼 × 2축에서 `SampleTestPlan` 의 인덱스 범위와도 전부 일치한다(독립 검산).

### Camtek T254 — 장비 화면이 `col_origin=2`·`ceil` 폴백을 확인해 준다

16호기 장비 화면 판독 2건. 이 웨이퍼는 `Center_X=Center_Y=0.000000`(미기록)이라
**폴백 경로**를 탄다:

| 사진 | INI Col/Row | 장비 화면 | 앱 |
|---|---|---|---|
| `29648.164545.c._2_` | 2 / 5 | **0, 5** | 0, 5 ✓ |
| `84722.113001.c._1_` | 5 / 3 | **3, 7** | 3, 7 ✓ |

`col_origin = 2`, `row_total = ceil(300000/31109.8) = 10` — 즉 **폴백값이 이 자재에서는
정답**이다. §6-J 의 변경이 이 사례를 깨지 않는다는 확인이기도 하다.

교차 검산: KLA T254 의 `SampleCenterLocation` 과 정렬식으로 역산한 Camtek 중심은
`Center_Y ≈ 202326` 이고, 그 값을 유도식에 넣으면 `row_total = 10` 이 나온다 —
**폴백값과 유도값이 이 자재에서는 같다**(TB500 에서는 7 vs 6 으로 갈린다).

### 남은 빚 — `Center_Y` 미기록 + TB500 격자

`Center_*` 미기록은 흔하다(T254 · TBD-PIDS3 · RDL1). 그때 `row_total` 은
`ceil(Diameter/pitch_y)` 로 폴백하는데, **T254 에서는 맞고 TB500 에서는 1 크다**
(정답 6, 폴백 7). `Center_Y` 없이 구분할 방법이 없다 — 관측된 `y_index` 최댓값으로
추정하는 건 결함이 적은 웨이퍼에서 크게 틀리므로(T254 는 관측 5, 정답 10) 쓰지 않는다.

영향: 그런 폴더에서 Camtek row 가 KLA row 보다 1 크게 나온다. `±1` 게이트 안이라
**매칭은 정상**이고 표기만 어긋난다. 닫으려면 **`Center_Y` 가 기록된 TB500 웨이퍼**가
필요하다(`좌표_검증_필요자료.md` ③).

회귀 가드: `test_wafer_geometry.py::TestKlaZeroFromSampleCenter`(장비 확인 7건 ·
`zero_y` 가 device 마다 다름 · `SampleTestPlan` 교차검산),
`::TestRealSamples`, `test_coords.py::test_real_pair_kla_camtek_rows_align`(남은 빚을 명시).

## 6-L. `Center_X/Y=0` 일 때의 진짜 소스 — `Wafer2Table.ini` (11차)

§6-K 가 남긴 빚: `Center_*` 가 `0.000000`(정렬 정보 미기록)이면 `row_total` 을
`ceil(Diameter/pitch_y)` 로 **추측**하는데, T254 에서는 맞고 TB500 격자에서는 1 크다.
격자만으로 구분할 수 없으니 결국 **웨이퍼가 어디 놓였는지를 알아야** 한다.

### 스캔 결과 폴더에는 그 정보가 있었다 — 코드가 안 읽었을 뿐

사용자가 뽑아 준 폴더 목록에 파일이 **약 140개** 있었다(앱이 읽던 건 6개).
그중 `Wafer2Table.ini` 가 답이다:

```ini
[WAFER ALIGNMENT]
Wafer2Table_X=   0.9999932263    0.0012932406   -166254.5886308713
Wafer2Table_Y=  -0.0012932406    0.9999932263   -202412.7818198704
[ANCHOR POINTS]
Anchor_1=158331.042831 186603.091890 -7681.375999 -16013.833047 …
```

두 줄이 어파인 변환 **`wafer = M·table + t`** 다. 같은 파일의 앵커 3점이
**2.7 µm 안에서 재현**되므로 방향이 확정된다(반대로 읽으면 중심이 음수가 된다).
웨이퍼 중심은 `wafer=(0,0)` 인 지점이므로:

```
중심(stage) = M⁻¹ · (−t) = (165993.7, 202628.8)
```

### 장비 화면 정답을 그대로 낸다

이 스캔(`GX57001305`, T254)의 `Params_WaferInfo.ini` 는 `Center_X=Center_Y=0.000000` 이다.
위에서 푼 중심을 §6-H·§6-J 의 식에 넣으면:

| | 유도값 | 장비 화면(§6-K) |
|---|---|---|
| `col_origin = ceil((Cx − D/2)/pitch_x)` | **2** | 2 ✓ |
| `row_total = floor((Cy + D/2)/pitch_y) − 1` | **10** | 10 ✓ |

교차 확인: KLA T254 헤더의 `SampleCenterLocation` 과 정렬식으로 **독립적으로** 역산한
`Center_Y ≈ 202326` 과 303 µm 차이다 — 서로 다른 두 경로가 같은 값을 가리킨다.

### 어떻게 바꿨나

중심 소스를 **우선순위 체인**으로 만들었다(pitch 후보와 같은 관습):

1. `Params_WaferInfo.ini [Geometric] Center_X/Y` — 기록돼 있으면(≠0) 1순위
2. **`Wafer2Table.ini` 의 변환을 풀어서** — `Center_*` 가 0 인 스캔의 실제 소스
3. 둘 다 없으면 옛 폴백(`CAMTEK_COL_OFFSET`, `ceil(Diameter/pitch_y)`)

특이행렬·비상식 값·`Y` 줄 누락은 채택하지 않는다(경고 후 폴백) — 추측 좌표를 내느니
폴백이 낫다는 기존 원칙 그대로다.

### ⚠ 1차 검증의 결함 — 서로 다른 웨이퍼를 섞었다 (사용자 지적)

위 검증은 **세 웨이퍼를 교차**한 것이었다. `Wafer2Table.ini` 는 웨이퍼마다 측정되는
값(`SaveTime`·앵커 8점·`StdAffine`)인데, die 맵 번호는 **레시피 단위 속성**이어야 한다.
웨이퍼별 측정값에서 레시피 단위 숫자를 유도하는 건 원칙적으로 위험하다.

| 자료 | 웨이퍼 |
|---|---|
| 장비 화면 `0,5` | `GIX5703110` |
| 장비 화면 `3,7` | `GIX5703111` |
| `Wafer2Table.ini` | `GX57001305` |

**실물 6건으로 닫았다**(`_wafer2table_모음/Wafer2Table_6건.md`):

**(1) 같은 웨이퍼 검증** — `GIX5703110` **자신의** 파일이 `col_origin=2`, `row_total=10`
을 내고, 그 웨이퍼의 장비 화면 판독값 `(0,5)` 와 정확히 맞는다. 지적이 닫혔다.

**(2) 웨이퍼 간 편차는 무시할 수준** — 같은 로트 3장(`GIX5703110`·`GIX5703114`·
`GX57001305`)의 중심이 **X 99 µm / Y 75 µm** 안에 모인다. 원점이 바뀌려면 X 로
**1594 µm**(경계까지 여유) 밀려야 하니 **16배 여유**다. 셋 다 `(2, 10)` 을 낸다.

**(3) 기록된 `Center_*` 와도 일치** — RDL4 계열 웨이퍼 2장(`XYB1`·`XYA2`)의
`Wafer2Table` 중심이 `Params` 기록값 `(167448.97, 179674.00)` 과 **140 µm** 안에 들어오고,
**유도한 원점이 같다**(`col_origin=1`, `row_total=6`). 1순위와 2순위가 어긋나지 않는다.

### 곁가지로 확정된 것 — row 기준은 격자가 아니라 **위치**가 정한다

같은 TB500 격자(`pitch_y≈44905`)인데 계열마다 갈린다. **row 기준은 중심을 몰라도 역산된다** —
`row_total = 장비 row + floor(Y/pitch_y)` 이므로, 아래 세 건은 장비가 낸 숫자만으로 나온다:

| 계열 · 웨이퍼 | 근거 | y_index | 장비 row | `row_total` |
|---|---|---|---|---|
| RDL4 (4건) | 장비가 파일명에 적은 값 | — | — | **6** |
| PI4 `VLP-PDIS3 W6317098XYB5` | 장비가 파일명에 적은 값(INI 와 0.001 µm 일치) | 2 | 5 | **7** |
| PI4 골든 `BNN-PIDS3` #1 | 장비 화면 정답 | 5 | 2 | **7** |
| PI4 골든 `BNN-PIDS3` #2 | 장비 화면 정답 | 7 | 0 | **7** |

§6-K 가 "격자만으로 구분할 수 없다" 고 적은 것의 **직접 증거**다.

> ⚠ `UDS-PIDS3 35115E27EWD7` 의 중심 `224,380` 도 같은 7 을 내지만 **근거가 약하다** —
> `Wafer2Table.ini` **한 장**에서 역산한 값이고(그 파일은 웨이퍼마다 측정된다),

> 중심을 확실히 하려면 무엇이 필요한지는 `좌표_계산_검증_보고서_상세.html` §9-1-A 참조.

## 7. 어떻게 바꿨나

새 모듈 **`aoi_verification/app/coords/wafer_geometry.py`** 가 폴더별 die 격자 기하를 제공한다.
`coords/pixel_size.py` 가 이미 "상수처럼 보이던 0.77 을 폴더에서 읽어 대체" 한 선례가 있어
그 관습을 그대로 따랐다 — 폴더 단위 `@lru_cache`, 우선순위 소스 튜플, 전 구간 fail-safe.

```
camtek_geometry(folder) → CamtekGeometry(pitch_x, pitch_y, col_origin, row_total, source)
kla_geometry(folder)    → KlaGeometry(pitch_x, pitch_y, zero_x, zero_y, source)
```

- **Camtek**: 폴더 → 부모 2단계까지 §5-C 의 후보 파일을 찾고, **검산(§2)을 통과한 첫
  후보**를 쓴다(실제 배치가 `…\<Lot>\<WaferID>\Params_WaferInfo.ini` 라 사진이 하위에
  있을 수 있다). `models.py` 상수도 마지막 후보로서 **똑같이 검산을 받는다**.
  통과한 후보가 없으면 `None` → 좌표를 만들지 않고 경고를 남긴다.
- **KLA**: `.001` 헤더 64 KB 만 읽어 `DiePitch` 와 `SampleTestPlan`(zero_x) 파싱.
- 폴백·거부 경로는 **반드시 경고 로그를 남긴다** (조용히 옛 경로로 떨어지면 아무도
  모른다 — `AsyncInferQueue` 때 겪은 그 사고).

`models.py` 의 pitch 상수는 이제 **마지막 검산 후보**이고, 맵 원점 상수 4개는 §8 참조.

## 9. 남은 상수 정리 — 무엇이 남았고 왜 괜찮은가

3차 조사(§6) 이후 남은 것:

| 상수 | 값 | 상태 |
|---|---|---|
| ~~`CAMTEK_ROW_TOTAL`~~ | — | **삭제** — `ceil(Diameter/pitch_y)` 유도(§6-A) |
| `CAMTEK_COL_OFFSET` | 2 | pitch 가 전혀 다른 3개 device 에서 불변 — **고정 시스템 오프셋**으로 판단(§6-B). 물리적 의미만 미확정 |
| `KLA_ZERO_X` | 3 | `.001` `SampleTestPlan` 에서 자동 산출(가장자리 열이 전부 사용될 때 유효) |
| `KLA_ZERO_Y` | 4 | `SampleTestPlan` 최솟값으로는 유도 불가 — TB500 실측 상수(§6-D). **`SampleCenterLocation` 기하는 3 을 낸다(§6-I)** — `row_total` 과 커플링돼 있어 장비 맵 화면 1장이면 둘 다 닫힌다(`좌표_검증_필요자료.md`) |

과거 시도 기록(참고):

| 방법 | 결과 |
|---|---|
| `ProductInfo.ini` 의 `Cols`/`Rows` | ✗ 두 예시를 동시에 설명하는 규칙이 없다(§5-A) |
| 웨이퍼 1장의 INI 에서 `min(Col)`/`max(Row)` | ✗ 웨이퍼마다 다르다(예시1 은 Col 2..8, 예시2·3 은 3..8) |
| KLA `SampleTestPlan` 인덱스 최솟값 | △ X 는 되지만 Y 는 안 된다(§1-B) |
| `ceil(Diameter/DieStep_Y)` | **✓ row 기준으로 채택**(§6-A) — 단 격자 '개수'(col 범위)는 여전히 못 준다 |

### 다른 자재로 바꿀 때 무엇을 보고 알 수 있나

- die pitch·row 기준은 폴더에서 유도되므로 **자동으로 맞는다**(검산 실패 시 좌표 없음 + 경고).
- `col − 2` 는 3개 device 실측상 불변 — 만약 어떤 자재에서 col 이 일정하게 어긋나면
  이 전제가 깨진 것이니 그 자재의 장비 화면 판독값을 확보할 것.
- KLA 단독/교차 검증에서 row 가 일정하게 어긋나면 `KLA_ZERO_Y` 가 그 자재와 다른 것 —
  동일 결함 쌍(Camtek↔KLA) 하나면 재확정할 수 있다(§1-B 방식).
- die 크기가 다른 자재로 바꾸면 Setup 화면의 die 크기 안내(§5-E)가 먼저 알려준다.
