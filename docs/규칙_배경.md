# 규칙 배경 — 왜 그 규칙이 생겼나

`CLAUDE.md` 는 **매 요청마다 컨텍스트로 실려 가는** 파일이라, 실행 가능한 규칙만 짧게 둔다.
규칙을 만들게 한 **사고 기록·실측 근거**는 길지만 매번 읽을 필요가 없어서 이 문서로 옮겼다.

규칙 자체를 고치거나 "이 규칙 왜 있지?" 가 궁금할 때만 여기를 본다.
`CLAUDE.md` 의 각 항목은 이 문서의 같은 제목을 가리킨다.

---

## 자동 업데이트 — '업데이트했다는데 안 바뀐다' 사고

세 가지 불변식은 각각 실제 사고에서 나왔다.

### 런처 exe 에 앱 코드가 들어가 최신 코드가 가려졌다
PyInstaller 의 `FrozenImporter` 는 exe 안 PYZ 에 들어 있는 사본을 디스크의 사본보다
**먼저** 찾는다. 런처 exe 를 빌드할 때 `aoi_verification` 이 함께 묶여 들어가면, 업데이트가
디스크의 `app/` 을 최신으로 갈아치워도 런처는 **exe 안에 굳어 있는 옛 사본**을 import 한다.
겉으로는 업데이트가 성공했다고 나오는데 동작이 그대로여서 원인을 찾기 어려웠다.

그래서 `exe_launcher.spec` 은 `hiddenimports` 가 비어 있어야 하고, `aoi_verification` 이
`excludes` 에 있어야 하고, `Analysis(pathex=[])` 로 저장소 루트를 주지 않아야 한다.
`build.py` 의 verify 가 `_internal/` 부재와 exe 용량으로 이를 재확인한다.

### 반쪽짜리 `app.new` 가 적용됐다
예전에는 스테이징 트리를 만들다 중간에 실패해도 "예외가 안 났으면 성공" 으로 취급해서
파일이 덜 복사된 트리가 적용됐다. 그래서 만드는 중에는 `app.new.part` 라는 이름을 쓰고,
검증을 통과한 뒤에야 `app.new` 로 rename 한다 — **그 rename 이 곧 '준비 완료' 신호**다.
별도 marker 파일을 두면 marker 와 트리 상태가 어긋날 수 있어 쓰지 않는다.

### 버전을 미리 써서 구버전을 영원히 실행했다
`_write_version` 이 살아있는 `app/VERSION` 에 새 버전을 먼저 써 버리면, 교체가 보류되거나
실패했을 때 앱이 "이미 최신입니다" 라고 판단해 **구버전을 영원히 실행**한다.
그래서 버전은 스테이징 트리에만 쓴다(`_write_version_to`).

## 테스트가 조용히 진짜 `pip` 을 돌렸다

`dev/tests/test_updater.py` 에서 모킹을 빠뜨린 테스트가 실제로 네트워크를 타고 패키지를
받으려 한 사고가 있었다. 테스트가 사용자 환경을 바꾸고, CI 에서는 느려지고 불안정해진다.
그래서 `_no_real_subprocess` 오토유즈 픽스처가 `subprocess.call` 을 아예 막고,
pip 동작 자체를 검증하는 테스트만 `_fake_pip` 로 덮어쓴다.

## 사내망 PyPI 차단은 '전언' 이었고, 실측은 열려 있었다

"사내망은 PyPI 가 막혀 있다" 는 말을 설계 전제로 삼을 뻔했으나, 실제로 측정해 보니
`pip download` 가 성공했고 인증서 오류도 없었다. 자동 업데이트의 의존성 설치 경로는
이 실측을 근거로 유지되고 있다.

**교훈: 검증되지 않은 전언을 설계 전제로 삼지 마라.** 막혀 있다고 들었으면 재 보고 결정한다.

## OpenVINO 심볼 위치가 바뀌어 비동기 추론이 조용히 죽었다

`AsyncInferQueue` 를 `openvino.runtime` 에서만 찾던 코드가 있었다. OpenVINO 2026.2 에서
그 네임스페이스가 삭제되자 `try/except` 폴백이 조용히 삼켰고, 추론이 **순차 경로로 떨어져**
한동안 느리게 돌았다. 결과 정확도는 같았기 때문에 아무도 눈치채지 못했다.

그래서 규칙은 "최신 위치를 먼저, 옛 위치를 폴백, **둘 다 없으면 경고**" 다
(`embedder_openvino._async_infer_queue_cls`). 조용히 실패하는 폴백을 남기지 않는다.
회귀 가드 `dev/tests/test_async_infer_queue.py` 는 torch 없이 `opset13` 으로 작은 모델을
만들어 **실제로 비동기 경로를 태운다** — 심볼 존재만 확인하면 같은 사고를 다시 놓친다.

## KLA WaferID 를 사진 파일명 prefix 로 추측했다가 되돌렸다

파일명은 형식 검증이 불가능하다. 기준·검증 **둘 다 KLA** 일 때 `FrontSideADRImg` 같은 공통
prefix 가 양쪽에 깔려 있어서, prefix 로 WaferID 를 추측하면 폴더가 그냥 **순서대로** 잘못
짝지어지고 슬롯이 뭉개졌다.

정보파일(`WaferID "XXXX";` 헤더)은 사진과 무관하므로 **사진이 0장인 폴더도 식별**된다.
그래서 `drop_empty_unmatched` 는 KLA 해석 **뒤**(`_after_slot_resolved`)에 돌아야 한다.
짝은 찾았지만 한쪽 사진이 0장인 슬롯은 `push_one_sided_to_unmatched` 로 '기준/검증 전용'
으로 되돌려 결과에 남긴다 — 그냥 두면 결과에서 통째로 사라진다.

## 임베딩 캐시 키에 버전 토큰이 없으면 매칭이 **틀린다**

임베딩 산출 방식을 바꾸고 `_EMB_VERSION` 을 올리지 않으면, 캐시 키(`_emb_signature`)가
같아서 옛 `.npy` 가 그대로 적중한다. 그러면 **같은 슬롯 안에서 옛 벡터와 새 벡터를 코사인
비교**하게 된다. 느려지는 게 아니라 결과가 틀리는 종류의 사고다.

같은 이유로 `ov.save_model` 의 `compress_to_fp16`(기본값 **True**)은 반드시 `False` 로 준다 —
FP16 반올림이 임베딩 값을 바꾼다. 변환 전 `.eval()` 도 필수다(BatchNorm 폴딩).

## 테스트 스위트가 3분 → 21초 (setStyleSheet 누적 비용)

`QApplication.setStyleSheet` 은 **부를수록 비싸진다.** Qt 내부 스타일 캐시가 프로세스 수명
동안 누적돼, 같은 호출이 세션 초반 1.4초에서 후반 5.9초까지 늘어났다(실측). 비용은 **살아있는
위젯 수와 무관**하다 — 위젋 0개인 시점의 호출이 5.9초였다.

테스트 모듈마다 `theme.apply_to_app` 을 부르는 `qapp` 픽스처를 각자 만들어 둔 탓에 호출이
21회였고, 그 합이 **82초 / 전체 181초** 였다. 조치:

- 테마 적용은 conftest 의 세션 스코프 `styled_qapp` 하나로 모아 **세션당 1회**.
- QSS **문자열만** 검사하는 테스트는 `theme.render_qss` 로 렌더해 문자열을 직접 본다
  (`setStyleSheet` 이 아예 필요 없다 — `test_sheet_size_and_edge` 참조).
- 파일 단위 병렬 실행(`-n auto`)을 추가.

결과: 3분 01초 → 1분 54초(위 두 조치) → **21초**(병렬까지). 실패·통과 수는 변동 없음
(807 passed, 3회 반복 동일 — 병렬에서 flaky 하지 않음).

`_qt_app` 픽스처 이름에 밑줄이 붙은 이유도 여기 있다: 테스트 모듈들이 `qapp` 을 자기 스코프로
재정의하는데, 세션 스코프 픽스처가 `qapp` 에 의존하면 그 재정의를 집어 ScopeMismatch 가 난다.

## '차이가 일정하면 통과' 로 pitch 검산을 완화하려다 안전장치를 뚫을 뻔했다

15호기 자재는 `ColorImageGrabingInfo.ini` 의 `Row` 필드가 **레시피마다 원점이 1 달라서**
`Row == floor(Y/DieStep_Y)` 검산이 깨졌고, 그 바람에 멀쩡한 `DieStep` 이 거부돼 좌표가
절대좌표 폴백으로 떨어졌다(→ `디바이스_하드코딩_조사.md` §6-F).

고치려고 **두 축 모두** '차이가 일정하면 통과' 로 완화하는 안을 먼저 잡았다. 검토 중
기존 테스트를 대조하다 잡았는데, 그러면 §5-B 의 핵심 안전장치가 뚫린다:

```
test_other_device_never_gets_tb500_numbers 픽스처 = INI 항목 **1건**
  → '차이가 일정' 이 공허하게 참
  → meaningful(Col=50, Row=20) 도 통과
  → PGEE48 자재에 TB500 상수(37247.7)가 채택 → x = −1,652,266 µm
```

즉 항목이 적은 폴더에서 '상수' 조건은 아무것도 제약하지 못한다. 실측을 다시 보니
**Δcol 은 11/11 전부 0** 이었다 — 완화가 필요한 건 Y 축뿐이었다. 그래서:

- **X: 등호 유지.** 기존 거부 경로 5종이 전부 X 축에서 걸린다(대조 확인).
- **Y: 레시피별로 차이가 상수.**

**교훈**: 검산을 완화할 때는 "무엇이 지금 걸러지고 있는지" 를 테스트 픽스처로 되짚어
확인할 것. 특히 **항목이 1건인 픽스처**는 집합 기반 조건(`len(set)==1`)을 공허하게
통과시킨다. 그리고 완화는 실측이 요구하는 축에만 한다.

## ±1 게이트가 흡수해 주는 어긋남은 버그가 아니라 **빚**이다

Camtek INI 와 LIVE 파일명은 같은 결함에 서로 다른 `row` 를 내고 있었다. `camtek_live` 가
row 토큰을 `−1` 하고 있었는데, 그건 `CAMTEK_ROW_TOTAL` 을 7→6 으로 바꾸던 변경과
**짝**이었다(`e90c48d`). 그 변경은 장비 화면 판독으로 곧 되돌려졌지만 **`−1` 만 남았다.**

그래도 매칭은 계속 됐다. `(col,row) ±1` 이웃 게이트가 1 어긋남을 흡수했기 때문이다.
아무도 몰랐다 — 다른 축이 1 더 어긋난 자재가 올 때까지는. 그 자재에서
`Δrow` 가 **2** 가 되면서 die 좌표가 0.48 µm 로 겹치는 쌍이 통째로 매치 실패했다.

**교훈**

- 게이트의 여유는 **장비 간 규약 차이**(KLA↔Camtek die 인덱스)를 위한 예산이지,
  우리 코드의 소스 간 불일치를 덮으라고 있는 게 아니다. 예산을 미리 써 버리면
  정작 필요할 때 모자란다.
- **소스 간 규약은 차이 0 으로 맞춰 두고**, 맞는지 테스트로 못 박아라
  (`test_coords.py::TestCamtekLive::test_matches_camtek_ini_convention`).
- 짝을 이루는 변경을 되돌릴 때는 **양쪽 다** 되돌렸는지 확인할 것. 커밋 메시지에
  "A 와 B 를 함께 바꾼다" 고 적혀 있으면, 되돌릴 때도 함께 봐야 한다.
- 회귀 테스트가 **정규화 자체**만 단언하면(입력 5 → 출력 4) 그 정규화가 옳은지는
  영영 검증되지 않는다. **두 소스가 같은 값을 내는지**를 단언해야 잡힌다.
