# Generate → Grade → Improve

복잡하고 주관적 품질이 중요한 창작/설계 작업(UI/디자인, 글쓰기, 아키텍처/코드 설계,
카피 등)에서, 여러 독립적인 대안을 만들고, 명시적 기준으로 채점하고, 기준 미달 항목만
정밀하게 고치는 4단계 루프. 이 접근의 핵심은 **다양성(서로 겹치지 않는 독립적 시도)**과
**엄격한 채점(관대하지 않은 다수 관점)**을 구조적으로 강제해서, 단일 에이전트가 자기 결과를
자기가 평가할 때 생기는 확증편향을 피하는 것이다.

## 언제, 얼마나 크게 적용할까

이 워크플로우는 비용이 크다 (여러 번 생성 + 여러 명이 채점 + 반복 개선). 그래서:

- **명시적 호출**이면 바로 진행한다.
- **암묵적 판단**(사용자가 이 스킬 이름을 말하지 않았지만 작업 성격상 잘 맞는 경우)이면,
  전체 프로세스를 먼저 돌리지 말고 **"이 작업엔 여러 안을 만들어서 채점 후 개선하는
  방식이 잘 맞을 것 같은데, 이렇게 진행할까요?"** 같은 한 줄 제안으로 먼저 동의를 구한다.
- 작업 규모가 작으면(예: 카피 한 줄, 함수 하나) 이 워크플로우를 쓰지 않는다 — 오버킬이다.

**모든 숫자(에이전트 수, 기준 개수, 채점자 수, 통과 점수, 최대 반복 횟수)는 고정값이
아니라 작업 규모·중요도에 맞춰 그때그때 판단한다.** 아래는 감(感)을 잡기 위한 기준점이지
규칙이 아니다:

| 작업 규모 | 대안 개수 | 기준 개수 | 채점자 수 | 통과 점수 (10점 만점) |
|---|---|---|---|---|
| 소규모 (카피 3안, 함수 설계 2안) | 2~3 | 5~10 | 2~3 | 8.0~ |
| 중간 (문서 초안, 컴포넌트 설계) | 3~4 | 10~15 | 3 | 8.5~ |
| 대규모/고난이도 (UI 전체, 아키텍처 설계) | 4~5+ | 20+ | 5 | 9.0~9.3+ |

사용자가 "최고 수준", "완벽하게", "애플급" 같은 표현을 쓰면 통과 점수를 높이고, 시간·
비용 제약을 언급하면 규모를 줄인다.

## 1단계 — 다양한 에이전트로 작성

- 동일한 과제에 대해 여러 개의 **독립적인** 대안을 만든다. "독립적"이 핵심 —
  단순히 톤만 다른 변주가 아니라 진짜 다른 접근/구조/전략이어야 한다.
- 모든 생성 주체에게 같은 핵심 브리프를 준다: 목표, 하드 제약(예: 기존 포맷/스키마,
  변경 불가 항목), 참고할 기존 결과물, 피해야 할 클리셰 목록.
- 서로 겹치지 않도록 **탐색 영역을 분배**한다 (예: "이미 다른 대안이 A 방향을 택했으니
  너는 B, C 방향은 피하라"). 기존 결과물이 있다면, 한 에이전트는 "그것만 개선"하는
  역할을 맡기고 나머지는 자유 구상하게 하는 식으로 역할을 나눌 수 있다.
- 병렬 서브에이전트(Task 등)를 쓸 수 있으면 동시에 실행한다. 쓸 수 없는 환경(예: 서브
  에이전트가 없는 채팅 세션)이면 순서대로 진행하되, 매번 진짜로 다른 관점/제약을
  채택해서 결과가 실질적으로 달라지게 한다 — 겉모습만 바꾸는 건 이 단계의 목적을
  훼손한다.
- 각 대안은 자체적으로 이해 가능해야 한다: 결과물 + 왜 그렇게 설계했는지 근거 1~2문장.
- **체크포인트**: 작업이 크고 이후 단계 비용이 크다면, 세부 완성 전에 각 대안의
  핵심 컨셉만 간단히 사용자에게 보여주고 방향이 맞는지 확인받은 뒤 다음 단계로
  진행한다. (잘못된 방향으로 다 만들고 나서 갈아엎는 것보다 훨씬 싸다.)

## 2단계 — 기준 생성

- 채점을 시작하기 **전에** 명시적이고 측정 가능한 채점 기준을 만든다.
- 기준은 구체적이고 관찰 가능해야 한다. "디자인이 좋다" 같은 모호한 항목 대신
  "본문 텍스트 대비 WCAG AA 실측", "핵심 정보가 스크롤 없이 보이는가", "문단당 한
  가지 주장만 담겼는가" 처럼 근거로 판정 가능한 항목으로 쓴다.
- 도메인에 맞게 항목을 구성한다 (UI라면 가시성/모션/반응형/접근성, 글쓰기라면
  구조/논지/톤 일관성/근거, 코드 설계라면 확장성/테스트 용이성/성능/가독성 등).
- 10점 만점 기준으로, "9점대는 예외적으로 뛰어날 때만"처럼 만점 인플레이션을
  막는 기준도 함께 명시한다.
- 기준 목록은 채점 전에 먼저 나열해서 투명하게 공개한다 — 모든 대안에 동일하게 적용.

## 3단계 — 채점

- 서로 **성격이 다른 채점자 페르소나**를 만든다. 단순히 "채점자 1, 2, 3"이 아니라
  실제로 다른 전문성/관점을 대표해야 한다 (예: 깐깐한 감사관, 실사용자, 스타일
  순수주의자, 안티-클리셰 비평가, 도메인 전문가 — 작업 성격에 맞게 구성).
- 채점자에게 명시적으로 지시한다: **"관대함 금지, 증거 기반으로만 채점, 최고점은
  진짜 예외적일 때만."** 이게 없으면 채점이 고무도장이 된다.
- 각 채점자는 모든 대안 × 모든 기준에 대해 점수 + 근거(왜 이 점수인지, 무엇이
  부족한지)를 남긴다. 숫자만 있고 근거가 없는 채점은 쓸모없다.
- 결과를 점수표(대안 × 기준 × 채점자)로 집계하고, 어떤 항목이 가장 낮은 점수를
  받았는지 눈에 띄게 표시한다.

## 4단계 — 개선

- **어떤 채점자든 어떤 항목 하나라도 통과 점수 미달이면, 그 항목만** 정밀하게
  고친다 (대안 전체를 다시 만들지 않는다 — 비용 낭비).
- 고친 항목만 해당 채점자에게 재채점받는다 (전체 재채점 아님).
- **최대 반복 횟수를 정해둔다** (기본 3~4라운드). 이게 없으면 무한루프에 빠질
  수 있다 — 완벽히 객관적인 채점 기준은 없기 때문에 특정 항목이 영원히 통과
  못 할 수도 있다.
- 최대 라운드를 넘겨도 미달인 항목은 계속 고치지 말고, **그 항목과 이유
  (트레이드오프)를 사용자에게 보고**하고 넘어간다. "완벽"을 무한정 추구하지 않는다.

## 최종 보고

- 주장("잘 만들었습니다")이 아니라 **증거**(실제 결과물, 스크린샷/파일, 점수표)로
  보여준다.
- 여러 대안이 최종 산출물이라면, 사용자가 직접 비교/선택할 수 있는 형태로 나란히
  제시한다.
- 어떤 항목이 몇 라운드 만에 통과했는지, 미수렴 항목이 있다면 무엇이었는지도
  간단히 요약한다.

## 원칙 요약

- 모든 숫자는 작업 규모에 맞춰 조정한다. 고정 공식처럼 쓰지 않는다.
- 암묵적 트리거 시엔 먼저 짧게 제안하고 동의를 구한다 — 비용이 큰 프로세스를
  말없이 돌리지 않는다.
- 크고 비용이 큰 작업은 중간 체크포인트(컨셉 승인 등)를 둔다.
- 개선은 항목 단위로 정밀하게 — 통째로 다시 만들지 않는다.
- 반복에는 항상 탈출 조건이 있어야 한다.
